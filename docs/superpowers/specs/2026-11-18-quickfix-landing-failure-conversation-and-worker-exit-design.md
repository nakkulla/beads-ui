# quick_fix 착지 실패: 해결 세션 자동 시작, hub, Worker 마무리 (UI-1fss)

## 1. 배경

2026-11-18 `dotfiles-jtuda`의 quick_fix attempt가 착지의 배포 단계에서
`script_failed`로 실패했다(자동 재시도 소진). 그 뒤 세 가지가 사용자의 기대와 달랐다.

1. 해결 세션이 자동으로 열리지 않았다. 카드는 14:45부터 사용자가
   `[세션에서 이어가기]`를 누른 15:46까지 대기만 했다.
2. 버튼으로 연 세션이 설정된 `hub`가 아니라 `dev` tmux 세션에 열렸다.
3. 대화가 "워커가 이어감 · 실패한 배포 단계를 한 번 다시 돌린다"로 끝났는데 Worker가
   `Worker로 넘김 거절 · 이미 정산됨`으로 받지 않았다. 행은 실패로 남았다.

사용자가 기대하는 흐름(2026-11-18): 이런 실패는 누르지 않아도 해결 세션이 `hub`에
열리고, 세션은 사용자의 답만 받으며, 답을 받으면 닫히고 Worker가 마무리까지 간다.

PR 경로의 배포 실패는 이미 이 흐름을 탄다. quick_fix 착지 실패만 자동 기동 대상과
인계 출구 양쪽에서 빠져 있다.

## 3. 목표

quick_fix 착지 실패가 실패 종단으로 적히면 사람의 클릭 없이 해결 세션이 설정 세션에
한 번 열린다. 그 대화가 `인계`로 끝나면 Worker가 실패한 착지 절차를 다시 실행해
마무리한다. 버튼으로 여는 대화 창도 설정 세션에 열린다.

## 4. 설계

### 4.1 자동 기동

- 결정: quick_fix 착지 안에서 저장소 작업(배포·검증)이 종단 실패하면 다른 실패 대화와
  같은 공용 스위치와 같은 기동 문(행당 살아 있는 대화 하나, 인계 예약)으로 해결
  세션을 연다. 시점은 그 실패로 attempt가 `failed`에 적힌 직후이고 배치는 설정
  세션이다. 계약의 `repo_operation_failure`를 이 경로에서도 지키는 것이다.
- 결정: 저장소 작업이 아닌 착지 단계의 실패와 대기로 분류되는 것(배포 조건 대기, 선행
  대기, 반영 대기)은 대상이 아니다. 앞의 것은 계약의 대상 목록에 없고, 뒤의 것은 각자의
  기존 사다리를 탄다.
- 결정: 한 번의 기준은 실패 기록 하나다 — 종단 실패한 저장소 작업 실행 하나에 한 번.
  1회 표시를 기동 전에 durable하게 쓰고, 재시작·재관측·reconcile은 다시 띄우지 않는다.
  이 기능 이전의 실패 기록은 표시가 없으므로 소비된 것으로 본다. attempt id는 정산
  재실행에서도 같으므로 기준으로 쓰지 않는다.
- 결정: 알림은 기존 `🙋 확인 필요 · <클래스>` 하나이고 클래스 낱말은 `착지 실패`다.
  기동 결과(창 자리 또는 미기동 사유)를 그 알림이 싣는다.
- 결정: 인계로 다시 실행한 착지가 같은 원인으로 또 실패하면 자동으로 다시 열지
  않는다. 카드의 `[세션에서 이어가기]`가 남는다 — 대화와 재실행이 사람 없이 도는
  고리를 막는다. 같은 원인의 기준은 같은 attempt, 같은 착지 단계, 같은 실패 코드다.
  실패 지문은 실행마다 달라질 수 있어 기준으로 쓰지 않는다. 단계나 코드가 다르면 새
  실패이므로 한 번 연다.

### 4.2 인계 출구

- 결정: 인계 대상에 quick_fix 착지 실패 종류를 더한다. 대상 식별은 §4.1의 실패 기록
  하나다(재실행이 끝나면 바뀐다). 출구는 카드의 `[↻ 정리 재시도]`와 같은 경로를 한 번
  실행하는 것이다 — 사람 클릭 한 번과 같고 자동 재시도 횟수를 쓰지 않는다.
- 결정: 기존 한 번 규칙을 그대로 따른다. 출구를 부르기 직전에 실행 시작을 대화
  레코드에 쓰고, 재시작한 pass는 지문이 바뀌었으면 실행된 것으로 본다.
- 결정: 재개가 지금 불가능한 행(카드의 `[↻ 정리 재시도]`가 비활성인 사유)은 같은
  사유로 인계를 거절한다. 행은 그대로이고 짝이 다시 선다.
- 결정: 이미 착지가 끝난 행(`landed`)의 출구도 같은 정산 재실행이다 — 남은 배포·정리만
  다시 돈다.
- 결정: 대화 진입 블록에 이 행의 출구를 한 줄로 알린다(인계하면 Worker가 실패한 착지
  단계부터 다시 실행한다). 세션이 인계를 고를 근거다.

- 결정: 해결 세션이 자가 수리로 끝난 경우(수리 이슈를 만들고 `수정 대기 ·` 결과 줄을 낸
  경우)에도 이 행이 같은 길을 탄다 — 수리가 착지하면 Worker가 사람 클릭 없이 실패한
  착지 절차를 한 번 다시 실행한다. 2026-11-18 사용자 결정: 해결 세션이 근본 원인을
  스스로 고치고 재시도까지 자동으로 간다. 수정 대기의 조건·한도·소진 뒤 사람 출구는
  기존 조항 그대로다.

### 4.3 거절 문구

- 결정: `이미 정산됨`은 대상이 있었는데 지문이 바뀐 경우에만 쓴다. 예약 때부터 대상이
  없던 행은 `이 행에는 Worker 출구 없음`으로 거절한다. 카드와 타임라인 문구가 함께
  바뀐다.

### 4.4 버튼으로 여는 창의 자리

- 결정: bdui가 클릭으로 여는 대화 창은 모두 자동 기동과 같은 설정 세션에 연다 —
  2026-11-18 사용자 결정. 해결 세션의 `[세션에서 이어가기]`, 멈춤 문의, 외부 작업
  이어가기가 대상이고, 이후에 더해지는 클릭 기동 대화 창(UI-6kj0의 일시정지 타일)도
  같은 규칙을 따른다. UI-a119 §3.1의 사용자 세션 우선을 뒤집는다.
- 결정: 클릭은 지금처럼 그 창을 설정 세션 안에서 현재 창으로 고른다. 사용자의 다른
  tmux 세션은 건드리지 않는다.
- 결정: 이미 사용자 세션에 열려 있는 대화 창은 옮기지 않는다. 그 창을 찾아 앞으로
  부르는 동작은 그대로다.
- 결정: 세션 레인의 창(UI-lbm5)은 바꾸지 않는다 — 대화 창이 아니라 작업 창이다.

### 4.5 대화의 수명

바꾸지 않는다 — 2026-11-18 사용자 결정(자가 수리 유지). 세션은 읽기 전용 진단 뒤
묻고, 결과 줄(`인계`·`인수`·`보류`)로 끝나며, `인계`는 창을 닫고 소멸을 확인한 pass가
출구를 실행한다. 계약의 자가 수리 조건을 채운 실패는 지금처럼 묻지 않고 고친 뒤 넘길 수
있다. 이번 사건에서도 대화는 3분 만에 `인계`로 끝났다 — 막힌 곳은 출구였다.

## 5. 비목표

- 실패 카드의 표시 — UI-lx9o.
- 자가 수리(수정 대기)의 조건과 한도 — UI-hozk 조항 그대로.
- PR 경로 실패의 자동 기동·출구 — 이미 있다.
- `dotfiles-jtuda` 배포가 실패한 원인(preauthorization probe) 자체의 수리 — dotfiles.
- Discord 스레드가 만들어지는 시점.

## 6. 테스트 범위

- 착지 실패가 실패 tier로 적히면 기동 함수가 설정 세션 배치로 한 번 불린다. 스위치가
  꺼져 있거나 살아 있는 대화가 있으면 불리지 않는다.
- 대기 tier 착지 실패(배포 조건 대기)는 자동 기동하지 않는다.
- 재시작·reconcile 뒤 같은 attempt로 다시 기동하지 않는다.
- 인계 대상 판정이 착지 실패 행에 새 종류와 지문을 돌려준다.
- 인계가 정산 재실행을 한 번 부르고, 실행 시작이 적힌 뒤 재시작해도 다시 부르지
  않는다.
- 인계 재실행이 같은 단계·같은 코드로 다시 실패하면 자동 기동이 없고(지문이 달라도),
  단계나 코드가 다르면 한 번 있다.
- 저장소 작업이 아닌 착지 단계의 실패는 자동 기동하지 않는다.
- 수정 대기로 끝난 착지 실패 행은 수리 착지 뒤 정산 재실행이 한 번 불린다.
- 대상 없는 행의 거절 문구와 지문이 바뀐 행의 거절 문구가 다르다.
- 클릭 기동이 설정 세션 인자로 창을 연다(해결 세션, 멈춤 문의, 외부 작업 이어가기).
- 이미 사용자 세션에 있는 창은 그 자리에서 찾아진다.

## 7. 수용 기준

1. 공용 스위치가 켜진 상태에서 quick_fix attempt가 착지의 배포 단계 실패로 끝나면,
   클릭 없이 `hub:resolve-<bead>` 창이 열리고 타임라인에 대화 시작 줄이 남는다.
2. 그 대화가 `인계`로 끝나면 창이 닫히고 착지 절차가 다시 실행된다. 성공하면 Bead가
   완료 줄로 간다.
3. 재실행이 같은 오류로 실패하면 카드가 실패로 남고 대화는 자동으로 다시 열리지
   않는다.
4. `[세션에서 이어가기]`를 어느 tmux 세션에 붙어서 누르든 창은 `hub`에 열린다.
5. 출구가 없는 행의 인계 거절이 `이미 정산됨`이라고 말하지 않는다.
6. 해결 세션이 수리 이슈로 원인을 고치고 수정 대기로 끝나면, 그 수리가 착지한 뒤 실패한
   착지 절차가 자동으로 다시 실행된다. 실제 사례: `dotfiles-jtuda`의 원인은 beads-ui
   코드(UI-v13s)였고, 계약의 자가 수리 조건(재현된 원인, 등록된 rig의 코드)에 든다.

## 결정 (ADR 후보)

- 전제: ADR UI-gmww — 실패 자동 대화의 1회 표시·공용 스위치·기동 문, 인계의 한 번
  규칙과 실행 전 거절 조항을 그대로 따르고 대상 종류만 더한다.
- quick_fix 착지 실패를 자동 기동 대상과 인계 출구에 더한다. 되돌리기 어려움: 대상
  목록과 출구 표를 서버 스케줄러, 인계 대상 판정, 알림 클래스, 카드의 짝 판정, dotfiles
  대화 진입 블록이 함께 읽는다. 대안: 클릭 전용으로 두고 출구만 더한다(사람이 카드를 볼
  때까지 실패가 멈춘다). 맥락 없이는 왜 PR 없는 실패에 대화가 열리고 누르지 않은 정리
  재시도가 도는지 알 수 없다.
  `summary`: "quick_fix 착지의 저장소 작업 실패도 실패 기록당 한 번 해결 세션을 자동으로 열고 인계는 정리 재시도 한 번이며 같은 단계·같은 코드의 재실패는 다시 열지 않는다 — 나머지 조항은 UI-gmww 그대로다" → ADR, supersede UI-gmww
- 클릭으로 여는 대화 창을 설정 세션에 연다 — 배치 인자 하나로 되돌릴 수 있고 UI-a119도
  ADR이 아니었다 → ADR 아님
- 대상 없는 인계의 거절 문구를 나눈다 — 문구 변경 → ADR 아님
