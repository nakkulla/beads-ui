# 소진된 전역 Codex 활성 계정을 창 여유 계정으로 되돌린다 (UI-tyc2)

## 1. 배경

UI-ftww(PR #380)는 창이 소진된(100%) 계정으로 도는 **Worker의 Codex attempt**를 창 여유 계정으로
옮긴다. 그런데 2026-10-20 저녁 크레딧을 쓴 Codex 호출은 Worker attempt가 아니라 Claude 세션의 리뷰
위임(codex-runner)이었다. codex-runner는 전역 활성 계정(`~/.codex`)으로 시작하고, hanmail은 크레딧이
있어 5h 창 100%에서도 실패하지 않는다. 실패가 없으니 후보 조회 API(`/api/codex/switch-candidate`)도
불리지 않고, gmail의 5h가 0%로 돌아온 뒤에도 hanmail이 활성으로 남아 크레딧을 썼다. UI-ftww 스펙 §3
비목표는 "launch 경계의 복귀는 이미 된다"고 적었지만, 크레딧이 있으면 launch가 실패하지 않으므로 그
전제가 이 경로에서는 성립하지 않는다.

사용자 원문(2026-10-21, Telegram Hermes): "자동전환을 선택한 경우에만 여유있는 계정을 전환에 허용한 계정
안에서 바꾸는거로 하고 기다림으로 한 경우에는 바꾸지 말고 전역 active 계정을 유지하도록 하자". 같은
요청에서 사용자는 dotfiles codex-runner 시작 시점 확인을 이번 범위에서 뺐고, 열린 질문 4개는 조사해서
스펙에서 확정하라고 맡겼다(§4.1).

## 3. 목표와 비목표

목표:
- 전역 활성 Codex 계정의 창이 소진(100%)됐고, 자동 전환(switch) 정책 저장소가 활성 계정과 함께 허용한
  계정 중 창 여유 계정이 생기면, 서버가 전역 활성 계정을 그 계정으로 바꾼다.
- 기다림(wait) 정책의 약속 — 자동으로 다른 계정을 고르지 않는다 — 을 이 전환이 깨지 않는다.

비목표:
- 실행 중인 호출의 계정 교체. 바뀐 활성 계정은 새로 시작하는 호출·세션부터 쓴다.
- dotfiles codex-runner 시작 시점 확인(사용자가 범위에서 뺌).
- Claude 활성 계정. Claude 후보 선택에는 크레딧 패스가 없다.
- Worker attempt의 계정 이동. UI-ftww의 실시간·디스패치·재개 복귀가 그대로 맡는다.

## 4. 설계

### 4.1 정한 갈림 (열린 질문 1~4)

- 결정 — **정책 기준(질문 1)**: switch 정책이고 Codex 허용 목록에 현재 활성 계정과 후보가 **함께** 있는
  저장소가 있을 때만 바꾼다. 후보는 그런 저장소마다 그 허용 목록의 사용자 순서로 고르고, 저장소는
  작업 공간 키 오름차순으로 보아 처음 나온 후보를 쓴다 (대안: switch 저장소 허용 목록의 합집합; 이유:
  합집합은 순서가 정해지지 않고, 어느 저장소도 함께 허용하지 않은 이동을 만든다. 지금은 허용 목록이 거의
  같아 결과가 다르지 않다). 활성 계정이 어느 switch 허용 목록에도 없으면 바꾸지 않는다.
- 결정 — **기다림 보호(질문 1)**: 등록 저장소 중 Codex 정책이 `wait`이고 Codex 저장소 기본 계정이 없는
  저장소가 하나라도 있으면 바꾸지 않는다. 그 저장소는 새 디스패치·보류 멤버 추종·기다림 receipt 재개가
  모두 활성 로그인으로 떨어지므로, 활성을 바꾸면 기다림 저장소의 계정이 자동으로 바뀐다. 저장소 기본
  계정을 둔 기다림 저장소는 활성 전환의 영향을 받지 않으므로 막지 않는다. Bead 핀은 보지 않는다(핀 없는
  Bead가 언제든 생길 수 있다) (대안: 보류 멤버가 있을 때만 막기; 이유: 새 디스패치와 이미 멤버십이 지워진
  receipt 재개를 놓친다. 대안: wait 저장소가 있으면 무조건 막기; 이유: 기본 계정으로 격리된 저장소까지
  막으면 지금 설정에서 기능이 서지 않는다).
- 결정 — **트리거(질문 2)**: 현재 활성 계정 창 하나라도 `pct ≥ 100`일 때만 바꾼다. 크레딧 잔액·허용
  여부는 보지 않는다 (대안: 크레딧을 쓰는 중일 때만; 이유: UI-ftww와 같은 소진 판정을 쓰고, 크레딧이 없는
  소진 계정도 다음 호출마다 헛 한도 실패를 낸다). 수동 선택 기록은 두지 않는다. 활성이 100% 미만이면
  사람이 고른 계정이라도 건드리지 않으며, 바꾸면 알림을 남긴다(§4.4).
- 결정 — **왕복 방지(질문 3)**: 쿨다운을 두지 않는다. 후보는 창 여유(5h ≤ 80%, 그 밖 ≤ 90%)여야 하고
  트리거는 100%라, 다시 바꾸려면 새 활성 계정이 100%에 닿고 다른 허용 계정이 창 여유로 돌아와야 한다.
  크레딧 계정으로는 옮기지 않는다(`kind: 'preempt'`).
- 결정 — **주기(질문 4)**: 서버가 파싱한 Codex 목록마다(화면·Worker 패스·크레딧 폴러·후보 조회 API의
  읽기) 판정하고, 마지막 관측에서 활성 계정이 소진이면 60초 주기로 캐시 목록을 다시 읽는다. 소진을 이미
  관측해 타이머가 돌고 읽기가 성공하면, 다른 계정 리셋 뒤 복귀까지 최대 약 4분(60초 + 캐시 180초)이다.
  소진을 처음 관측하는 시점은 기존 읽기에 기댄다: 크레딧을 허용한 계정이 있으면 10분 폴러가 상한이고,
  크레딧 폴러가 꺼져 있고 화면·Worker·후보 조회 읽기도 없으면 상한이 없다(그때 소진 계정은 크레딧이 없어
  다음 호출이 실패하고, 세션은 후보 조회 API로 그 호출을 옮기며 그 읽기가 소진을 관측시킨다) (대안: 늘
  도는 60초 타이머; 이유: 소진이 아닐 때 codex-auth API 읽기를 늘리지 않는다).

### 4.2 판정 패스

서버 전역 모듈 하나(예: `server/codex-active-return.js`)가 맡는다. 입력은 파싱된 Codex 목록이다.

1. 활성 계정 행이 없거나 창이 모두 100% 미만이면 끝(소진 타이머가 돌고 있으면 멈춘다).
2. 소진이면 60초 타이머를 켠다(이미 돌면 그대로).
3. §4.3 거름을 통과하고 §4.1 정책 기준으로 후보가 나오면 확정 단계로 간다.
4. 결정 — **확정 단계는 수동 전환과 같은 잠금 안에서 한다**: 먼저 `in_flight_providers`에 `codex`를 잡고
   (이미 잡혀 있으면 이번 판정을 버린다), 잠금을 쥔 채 `listAccountsFresh`로 새로 읽고, 그 뒤 정책·보류·
   실행 중 attempt·저장소 기본 계정을 다시 읽어 1~3을 새 활성 기준으로 다시 판정하고, 후보가 나오면 전환을
   실행한 뒤 잠금을 푼다 (대안: 잠금 없이 새로 읽고 전환 직전에만 잠금; 이유: 새로 읽은 뒤 확인하는 사이
   끝난 수동 전환을 자동 패스가 낡은 판정으로 덮어쓴다). 잠금을 쥔 동안 들어온 수동 전환 요청은 지금처럼
   409 `switch_in_flight`로 답한다.
5. 전환 실행은 수동 전환과 같은 경로다: `codex-auth switch`, 성공 시 캐시 무효화와
   `notifyAccountSwitched('codex')`. 예: account-switch.js가 잠금 획득·해제와 실행을 핸들러와 공유하는
   함수로 내보낸다. 그래서 기다림 추종·캐시 반응은 수동 전환과 똑같다.
6. 패스는 한 번에 하나만 돈다. 진행 중이면 새 관측은 건너뛴다.

### 4.3 거름

아래 하나라도 서면 이번 판정은 바꾸지 않는다(다음 관측·주기에 다시 본다).

1. 수동 전환이 진행 중(`in_flight_providers`에 `codex`).
2. 어느 저장소든 `running` Codex attempt가 계정 없이(`activeAccountOf` null) 돈다 — 그 attempt는 활성
   로그인의 인증 파일을 읽는다.
3. 후보를 `running` attempt가 `codex_account`로 쓴다 — 그 후보는 제외하고 다음 후보를 본다(수동 전환의
   토큰 갱신 충돌 확인과 같은 이유).
4. §4.1 기다림 보호에 걸린다(기본 계정 없는 Codex `wait` 저장소가 있다).
5. 보류(`provider_hold` target) 중인 계정은 후보가 아니다(기존 선택 규칙).

### 4.4 보이는 것

새 라벨·칩·버튼은 없다. 바꾸면 Worker 알림기로 `ops` 알림 하나를 보낸다. 예:
`🔁 Codex 활성 계정 자동 전환 — 계정 #3 → 계정 #1` / `#3 <창> 100% · 새로 시작하는 호출부터 적용`.
서버 로그에 같은 내용을 남긴다. 사용량 카드는 캐시 무효화로 다음 읽기에 새 활성을 보인다.

기다림 보호(§4.3-4)만 때문에 바꾸지 못하면(다른 조건은 모두 서고 후보도 있음) 소진 구간마다 한 번 `ops`
알림을 보낸다. 예: `⏸ Codex 활성 계정 자동 전환 보류 — 기다림 저장소 <이름>이 활성 로그인을 씀` /
`그 저장소에 Codex 기본 계정을 정하면 다음 판정부터 전환합니다`. 소진 구간은 활성이 소진으로 관측된
때부터 소진이 아니게 관측될 때까지다.

### 4.5 오류와 경계

- 목록 읽기 실패 → 판정하지 않고 소진 타이머 상태도 바꾸지 않는다. 창 정보 없는 행 → 소진이 아니다(바꿀
  근거가 없다).
- `codex-auth switch` 실패·시간 초과·출력 이상 → 로그만 남기고 다음 주기에 다시 본다. 알림은 보내지 않는다.
- 저장소 정책 읽기 실패 → 그 저장소는 기준에서 빠진다.
- `wait` 저장소의 Codex 기본 계정 읽기가 실패하면(kv 실패·layer `unusable`) 그 저장소는 기본 계정이
  없다고 보고 막는다(바꾸지 않는 쪽으로 실패).
- 사용자가 소진된 계정을 일부러 활성으로 두고 싶으면 그 계정을 switch 허용 목록에서 뺀다. 활성이 어느
  switch 허용 목록에도 없으면 바꾸지 않는다(§4.1).

## 5. 테스트와 수용 기준

공통: 활성 03(5h 100%, 크레딧 있음), 01 0%, beads-ui 정책 switch 허용 [01, 03], 실행 중 attempt 없음.

1. 공통 조건 → 01로 전환, 캐시 무효화, `notifyAccountSwitched('codex')`, ops 알림 1회.
2. 03이 99% → 전환 없음, 소진 타이머 꺼짐.
3. 01도 100%이고 다른 허용 계정이 크레딧만 있음 → 전환 없음(크레딧 계정으로 안 감).
4. 03을 허용한 switch 저장소가 없음(정책 wait이거나 허용 [01]만) → 전환 없음.
5. switch 저장소 A는 [03]만, B는 [01]만 허용 → 전환 없음(함께 허용한 저장소 없음).

   (같은 소진 구간의 다음 판정은 알림 없음). 그 저장소에 Codex 기본 계정이 있으면 → 전환.

7. 계정 없이 도는 `running` Codex attempt가 있음 → 전환 없음.
8. 01을 `running` attempt가 쓰고 허용 [01, 02, 03]에서 02가 창 여유 → 02로 전환.
9. 새로 읽은 목록에서 03이 리셋돼 100% 미만이거나 활성이 01로 바뀌어 있음 → 전환 없음.
10. 수동 전환 진행 중 → 전환 없음. `codex-auth switch` 실패 → 알림 없음, 다음 주기에 재판정.

     활성 02(창 여유) 기준으로 판정해 전환하지 않는다.
11. 소진 관측 뒤 60초 주기가 캐시 목록을 읽고, 소진이 아니게 관측되면 멈춘다.

## 7. 결정 (ADR 후보)

- 전제: ADR UI-ftww — 창 여유 우선·선제 선택은 크레딧으로 가지 않음·크레딧 설정 서버 전역·소진 판정
  100%·기다림 모드 추종(UI-np4t 승계) 조항을 그대로 따른다.
- 전역 활성 Codex 계정이 창 소진(100%)이면 서버가 switch 정책 저장소 중 활성과 후보를 함께 허용한
  저장소의 순서로 창 여유 계정을 골라 활성 계정을 바꾸고, Codex 기본 계정 없는 기다림 저장소가 있거나 계정
  없이 도는 실행이 있으면 바꾸지 않는다. ① 되돌리기 어려움: 공유 인증 상태(`~/.codex`)를 서버가 스스로 바꾸고,
  수동 전환 경로·기다림 추종·세션 codex-runner·사용자 터미널의 codex가 함께 그 결과를 받는다. ② 맥락 없이는
  놀라움: 사람이 고른 활성 계정이 알림과 함께 바뀌고, 기다림 저장소가 있어도 바뀔 수 있다. ③ 대안 실재:
  합집합 기준, wait 저장소가 있으면 금지, 크레딧 사용 중일 때만, dotfiles 시작 시점 확인. UI-ftww와 소비자
  (후보 선택·소진 판정·기다림 추종)가 같고 그 소진 복귀 조항을 전역 활성으로 넓히므로 재진술이다 —
  `summary`: "Codex 자동 전환 후보는 허용 목록의 사용자 순서로 창 여유 계정을 먼저 고르고 반응 전환에서만 계정별 크레딧 허용·하루 상한(다음 선택만 막음) 안의 크레딧 계정을 고르며, 창이 소진된 계정으로 도는 Codex 실행은 preempt_pct와 무관하게 창 여유 계정이 생기면 그 계정으로 옮기고, 전역 활성 Codex 계정이 소진되면 활성과 후보를 함께 허용한 switch 저장소가 있을 때만 서버가 창 여유 계정으로 바꾸되 Codex 기본 계정 없는 기다림 저장소가 있거나 계정 없이 도는 실행이 있으면 바꾸지 않으며, 크레딧 설정은 서버 전역이고 세션은 같은 규칙의 후보 조회 API를 쓰고, 세션이 맡긴 다른 러너 리프의 계정 한도로 끝난 attempt는 그 리프 계정 보류의 교차 멤버로 전환·기다림 추종 없이 해제 뒤 자기 러너 계정 규칙으로 재개한다 — 나머지 조항은 UI-np4t 그대로다" → ADR, supersede UI-ftww
