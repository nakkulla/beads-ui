# 연결 레인 제거와 저장소별 선행 대기·모니터 이동·리뷰 설정 표시

- 작업: UI-wc67
- 작성: 2026-09-14
- 상태: 사용자 검토용 초안, 구현 미착수
- 조사 기준: `origin/main`의 `80493d3103209e7d574f1acf2e6e55802657d2cc`
- 경로: `spec_backed`. 한 저장소·한 구현 소유자·한 검증 및 PR 묶음으로 완료한다. 별도 착지나 다른 실행 소유자에게 넘겨야 하는 중간 단계는 없다.

## 1. 요구와 확인된 현재 동작

사용자는 모니터의 크로스레포 연결 레인을 완전히 없애고, 각 저장소의 병렬 또는 직렬 대기열에 넣은 이슈가 외부 의존성을 기다리는 동안 다른 이슈가 진행하기를 요청했다. 모니터에서 프로젝트 드롭다운을 선택하면 해당 저장소의 Worker 탭으로 이동하고, 저장소 카드의 `미확인` 의미를 명확히 하며 구현 리뷰 모델·effort도 보여 달라는 요청을 함께 처리한다.

현재 ADR 0041은 연결 레인 제거를 결정하지 않았다. 연결 레인의 확정은 의존만 만들고, 진행은 기존 대기 위치를 보존하면서 실행 권한을 부여하도록 정했다. 이번 변경은 그 결정을 대체한다.

외부 선행 완료 뒤의 자동 재검사는 이미 연결 레인과 무관하게 구현되어 있다. `scheduler.js`의 `recordNotReady`는 실제 미해결 `blocks` 선행을 `prerequisite_unmet`으로 기록하고, `runWaitingRescan`과 `attach.js`의 `holdsWaitingOn`이 외부 저장소 활동을 받아 다시 실행 가능 여부를 확인한다. 병렬 대기열은 막힌 항목 다음도 살핀다. 직렬 레인은 현재 맨 앞 항목만 후보로 만들고, `laneLaunchRefusal`도 맨 앞이 아니면 거부하므로 같은 레인의 뒤 항목은 진행하지 못한다.

프로젝트 드롭다운은 `app/main.js`의 `handleWorkspaceChange`만 호출하여 탭을 유지한다. 모니터 카드의 기존 `Worker ↗`는 저장소 전환 후 탭 이동을 이미 구현한다.

카드의 `미확인`은 실행 설정이 아닌 저장소 건강 점검 정보다. `repo_health` 기록이 없거나 유효하지 않은 경우, 아직 비동기 조회가 끝나지 않은 경우, 조회가 실패한 경우가 모두 현재의 `unknown`으로 표시된다. 구현 리뷰 모델·effort는 기존 `session_defaults`와 `execution_defaults`에 이미 전달되지만 카드가 표시하지 않는다.

## 2. 선택한 방식과 대안

의존 관계와 실행 위치를 두 군데에서 관리하는 비용을 없애기 위해 **연결 레인을 제거하고 저장소별 대기열과 기존 `blocks` 의존만 사용한다**. 직렬 레인은 의존성을 기다리는 항목을 건너뛰면서 한 번에 하나만 실행한다.

- 연결 레인을 화면에서만 숨기는 방식은 전용 메시지·저장소·진행 권한과 관리 비용이 남으므로 채택하지 않는다.
- 별도 크로스레포 대기 영역이나 새 보류 상태를 만드는 방식은 같은 순서와 대기를 중복 관리하므로 채택하지 않는다.
- 기존 직렬 선두 규칙을 유지하면 변경은 작지만 앞의 선행 대기 때문에 뒤의 실행 가능한 이슈까지 멈추므로 사용자 요구를 충족하지 못한다.

## 3. 저장소별 실행 규칙

### 3.1 의존 관계와 배치

의존 관계의 정본은 기존 `blocks` 간선이다. 이슈 상세의 의존성 편집기로 같은 저장소 또는 외부 저장소 이슈를 선행으로 지정하고, 실행할 이슈는 자신의 저장소 병렬·직렬 대기열에 배치한다. 연결 레인에서 만들었던 의존도 일반 `blocks` 간선으로 그대로 남는다.

대기 이슈는 현재 레인·순서·대기 진입 시각을 유지한다. 선행을 기다린다는 이유로 다른 레인으로 이동하거나 맨 뒤에 다시 넣지 않는다. 선행 대기는 실패나 사용자 답변 대기가 아니며, 새 상태·metadata·별도 대기열을 만들지 않는다.

### 3.2 직렬 레인의 실행 가능한 첫 항목

직렬은 **한 번에 한 작업만 진행한다**는 뜻을 유지하고, 순서는 선행 의존을 기다리는 항목을 제외한 나머지 항목 사이에서 지킨다. 같은 저장소와 외부 저장소의 `blocks`에 같은 규칙을 적용한다.

예를 들어 직렬 대기열이 `A → B → C`이고 A가 외부 선행 X를 기다리면, A는 같은 자리에 둔 채 B를 실행한다. B의 기존 직렬 점유가 해제될 때까지 C나 A를 동시에 시작하지 않는다. 그때 X가 닫혔으면 A부터 다시 살피고, 아직 닫히지 않았으면 C를 살핀다. 실행 중인 B를 중단하거나 선점하지 않는다.

선택 규칙은 다음과 같다.

1. 기존 직렬 점유·실행 예약이 있으면 그 레인에서 새 작업을 시작하지 않는다. 실행 중·PR 대기·정리 중 계보의 기존 점유 해제 조건을 유지한다.
2. 비어 있는 직렬 레인은 저장된 순서대로 살핀다. 실제 미해결 선행이 확인되어 `prerequisite_unmet`으로 판정되는 항목만 건너뛰고 다음 항목을 살핀다.
3. 실행 가능한 첫 항목을 찾으면 그 레인에서는 한 건만 선택한다. 한 패스에 슬롯이 여러 개 남아 있어도 같은 직렬 레인에서 여러 건을 고르지 않는다.
4. 일시정지, 사용자 처분 대기, 유예, 관측 실패, 선행 이외의 실행 거부는 뒤 항목이 추월할 근거가 아니다. 이 경우 해당 레인의 탐색은 멈추고 다른 레인의 진행은 허용한다. 미해결 선행을 확인하지 못한 `not_ready:*`도 여기에 해당한다.
5. 이미 닫힌 이슈는 기존 완료 정리 절차로 대기열에서 제외한다. 선행 대기 예외를 다른 거부 사유까지 넓히지 않는다.

화면 후보 선택만 바꾸지 않고 `runPass`, 명시적 `[지금 시작]`, 실행 예약과 실행 직전 재검사의 맨 앞 판정을 같은 의미로 맞춘다. 자동 진행이 꺼져 있으면 의존 해소만으로 새 작업이 시작되지 않는다. `[지금 시작]`은 지정된 이슈에만 권한을 주며, 앞 항목들이 확인된 선행 대기일 때만 같은 직렬 순서 예외를 적용한다. 클릭한 이슈가 막혔다고 뒤의 다른 이슈에 실행 권한을 넘기지 않는다.

기존 동기식 실행 예약의 부작용 경계를 유지한다. 비동기 준비 확인 도중 순서·레인·앞 항목의 준비 상태가 바뀌면 최신 상태로 다시 판정하여 예약을 취소하거나 재선택한다. 맨 앞 거부를 단순히 삭제하거나 오래된 admission 기록만으로 순서를 추월하지 않는다. 새 영구 실행 권한이나 복구 상태를 추가하지 않는다.

### 3.3 선행 완료와 표시

기존 변경 감시·외부 저장소 활동 이벤트·시작 시 한 번의 재검사를 재사용한다. 요청 저장소의 `bd ready`로 실행 가능 여부를 판정하고, ready가 확인된 이슈의 선행 대기 표시를 지운 뒤 보통 스케줄링으로 돌아온다. 병렬·직렬 대기열 모두 같은 경로다.

직렬에서 건너뛴 항목에도 확인된 선행 목록을 기록하여 외부 선행 완료 이벤트가 해당 저장소를 깨울 수 있게 한다. 남아 있는 선행은 기존 `⛓ <ID>` 칩과 선행 대기 표시로 설명한다. 복귀 후에도 사용자가 고른 레인과 상대 순서를 유지한다.

외부 저장소를 찾지 못하거나 조회에 실패하면 선행이 해소됐다고 추측하지 않는다. 기존 진단 경로를 유지한다. 순환 의존은 자동으로 끊지 않으며, 가능한 다른 작업만 처리하고 당사자들은 대기한다.

## 4. 연결 레인 기능 제거

다음 전용 경로를 한 변경으로 제거한다.

- 모니터 연결 레인 패널, 추가·확정·진행·재적용·정지·삭제, 연결 레인 배치 메뉴·드롭·스크롤 이동.
- 공통 레인 모델의 연결 레인 투영과 멤버십·진행 권한 칩, 관련 CSS와 상태 저장 필드.
- `monitor-lane-*` 다섯 메시지, 전용 서버 핸들러·provenance 처리, 스냅샷의 `cross_lanes` 및 클라이언트 수신 상태.
- `cross-lanes-store.js`와 전용 읽기·쓰기, 연결 레인 멤버만을 위해 비어 있는 저장소를 추가하는 모니터 투영.
- 연결 레인 전용 `worker-queue-arm`/`worker-queue-disarm`, `armed_by_lane`의 새 권한 부여·실행·재적재·머지 등록 경로와 cold-load 해제 알림.

공유 드래그 계획 코드에서는 저장소별 병렬·직렬 배치와 순서 변경에 필요한 부분을 남기고 연결 레인 분기만 제거한다. 파일 이름만 보고 통째로 삭제하지 않는다. 일반 의존성 조회·편집, 외부 blocker 조회, 저장소별 직렬 레인, `[지금 시작]`, 기존 자동 진행·자동 머지 조작은 계속 사용한다.

기존 자료 처리는 다음으로 고정한다.

- `blocks` 간선, 저장소별 대기 항목과 순서, 실행 중 세션, 완료 이력은 제거하지 않는다. 이전 연결 레인의 provenance를 근거로 `dep-remove`를 실행하지 않는다.
- 기존 `cross-lanes.json`은 런타임이 더 이상 읽거나 쓰지 않는 퇴역 자료로 둔다. 읽기·마이그레이션·자동 삭제를 위한 호환 경로를 만들지 않는다. 그 파일에만 있고 어떤 저장소 대기열에도 없던 멤버를 자동 적재하지 않는다.
- 과거 큐/attempt 자료에 연결 레인 필드가 남아 있어도 실행·머지 권한으로 소비하지 않는다. 새 큐/attempt 정규화와 저장에서는 이 필드를 만들지 않고, 과거 이력 파일은 다시 쓰지 않는다.
- 이미 머지 대기열에 등록되어 있는 유효한 권한은 취소하지 않는다. 퇴역한 arm 필드에서 새 권한을 만들지 않는다. 자동 진행과 자동 머지는 계속 별개이며 기본값을 변경하지 않는다.

## 5. 프로젝트 선택 후 Worker 이동

프로젝트 드롭다운 전용 콜백에서 선택 당시 모니터였는지 기억하고 저장소 전환을 기다린다. 선택한 저장소가 현재 저장소로 확인되고 화면도 여전히 모니터이면 Worker 탭으로 이동한다. 전환 도중 사용자가 다른 탭을 골랐거나 더 최근 프로젝트 선택이 들어왔다면 이전 응답이 화면을 되돌리지 않는다.

전환 실패·잘못된 응답에는 기존 오류 처리를 적용하고 성공 이동을 하지 않는다. 이미 선택된 프로젝트를 다시 선택하는 이벤트도 해당 프로젝트의 Worker로 이어진다. Board·Worker 등 다른 탭에서의 프로젝트 변경은 현재 탭을 유지한다.

공통 `handleWorkspaceChange` 자체에 탭 이동을 넣지 않는다. 모니터 카드에서 이슈 상세를 여는 경로 등 다른 호출자의 의미를 유지한다. 기존 `Worker ↗` 버튼과 드롭다운은 성공한 저장소 전환 뒤 Worker를 여는 같은 동작을 갖는다.

## 6. 저장소 카드의 정보

### 6.1 건강 점검 정보

단독 `미확인`을 **`건강 점검 정보 없음`**으로 바꾼다. 설명은 **`저장소 건강 점검의 유효한 기록을 아직 확인하지 못했습니다. 기록 부재·조회 중·조회 실패가 포함되며, 실행 설정 오류를 뜻하지 않습니다.`**로 한다.

현재 producer가 구분하지 않는 원인을 클라이언트가 추측하지 않는다. 정상·오래된 기록·문제가 확인된 기존 상태와 관측 시각 표시는 유지한다. 건강 수집기나 캐시 정책을 바꾸지 않는다.

### 6.2 구현 리뷰 모델과 effort

저장소 카드의 기존 오케스트레이션·워커 설정 줄 뒤에 **`구현 리뷰 <모델> · <effort>`**를 표시한다. 이 값은 그 저장소의 다음 구현 리뷰에 적용할 기본 설정이며, 특정 이슈의 개별 설정이나 완료된 리뷰의 실제 실행 기록을 뜻하지 않는다.

기존 `deckExecChips`에서 호출하는 `resolveExecutionSettings`의 `impl_review_model`·`impl_review_effort` 결과를 사용한다. 저장소 `session_defaults`가 있으면 우선하고, 없으면 기존 배포된 기본값과 선택 리뷰어의 effort를 따른다. 모델·effort를 하드코딩하거나 서버에서 새로 계산하지 않는다. 툴팁은 모델 전체 이름과 각 값의 설정 출처를 알려 준다.

- 일반 리뷰어: 예시 `구현 리뷰 gpt-6-astra · xhigh`. 표기용 축약은 기존 모델 포매터를 따른다.
- `self`: `구현 리뷰 자체 검토`, effort는 적용되지 않으므로 표시하지 않는다.
- `skip`: `구현 리뷰 생략`, effort는 표시하지 않는다.
- 재료가 없으면 기존 카드와 같이 해당 정보를 생략한다. 모델만 확인되고 effort를 확인할 수 없으면 모델만 표시하며, 존재하지만 호환되지 않는 값은 기존 해석 결과의 진단을 따르고 다른 모델로 바꾸지 않는다.

이는 저장소 설정 카드의 정보 추가다. 이슈 카드에 새 리뷰 칩을 달거나 그 카드 슬롯을 확장하지 않는다. 이슈 카드의 기존 연결 칩을 제거할 때에는 카드 문법 정본의 §2 및 §5.1에서 해당 항목도 함께 제거한다.

## 7. 검증과 완료 기준

새 작업 체크아웃에서 Node 버전과 의존성을 확인한 뒤 기존 테스트에 다음 동작을 반영한다. 코드 작성 전에 실패 재현이 필요한 테스트 범위를 승인된 실행 단위에서 확정한다.

1. 외부 선행이 열린 A와 실행 가능한 B를 같은 직렬 레인에 두면 A의 위치를 보존하고 B만 시작한다. 선행 대기 항목이 여러 개여도 한 레인 한 실행을 지킨다.
2. B가 직렬 레인을 점유하는 동안 A의 선행이 닫혀도 추가 실행하지 않고, 점유 해제 뒤 A가 원래 순서에서 복귀한다. 모두 blocked이면 실행 없이 기다린다.
3. 같은 저장소 선행에도 같은 예외가 적용된다. 일시정지·관측 실패·의존 외 거부를 선행 대기로 오인해 추월하지 않는다. 자동 진행 꺼짐과 `[지금 시작]`의 지정 이슈 한정 권한을 지킨다.
4. 선택 확인 중 레인 이동·재정렬·선행 해소 및 동시 재검사가 발생해도 잘못된 순서 실행이나 직렬 중복 실행이 없다. 시작 예약·재검사 경로의 기존 경쟁 조건 테스트를 유지한다.
5. 병렬·직렬에서 외부 완료 이벤트가 막힌 이슈를 깨우며, 연결 레인 저장 자료가 없어도 작동한다. 기존 실패/해석 불가 경로를 유지한다.
6. 모니터와 Worker에서 연결 레인·메뉴·칩·전용 메시지가 사라지고 일반 레인 드래그·순서 변경·의존성 편집이 동작한다. 과거 arm 필드를 포함한 큐를 읽어도 새 실행/머지 권한이 생기지 않고 기존 대기열·의존·유효한 머지 권한을 보존한다.
7. 모니터 프로젝트 드롭다운에서 저장소 전환 성공 뒤 해당 Worker가 표시된다. 실패·잘못된 응답·빠른 연속 선택·전환 중 다른 탭 선택에서 잘못 이동하지 않으며 다른 탭의 프로젝트 선택은 탭을 유지한다.
8. 건강 정보 없음 문구와 설명, 구현 리뷰의 기본값·저장소 설정 우선·self·skip·결측·호환되지 않는 값 표시를 카드 테스트로 확인한다.

관련 기존 테스트는 `scheduler.test.js`, `attach.test.js`, 큐/자동 머지 테스트, 모니터·공유 레인 모델·드래그·카드·프로토콜 테스트와 `app/main.monitor.e2e.test.js`다. 제거한 기능만 시험하던 테스트는 삭제하고 보존 기능의 검증을 잃지 않는다.

최종 검증은 `npm run tsc`, `npm run lint`, 변경 파일 Prettier 적용, `npx vitest run --reporter=dot` 전체 실행(120초 제한)이다. 모니터/Worker 화면 확인에 필요한 빌드와 브라우저 검증을 수행한다. 잔존 검색으로 연결 레인 런타임 소비자가 없고 역사 문서·검증용 과거 자료만 남았는지 확인한다. ADR 인덱스와 인용 검사도 통과해야 한다.

## 8. 경계·후속

모든 요청은 이 저장소의 한 작업에 포함한다. 다른 저장소의 계약·건강 수집기, 설정 대화상자 재설계, 저장소 재탐색, 순환 의존 자동 수리는 이번 변경의 대상이 아니다. 별도 형제 작업이나 선행 작업은 필요하지 않다.

현재 체크아웃에 있는 별도 미추적 설정 대화상자 설계 파일은 수정하거나 포함하지 않는다. 이 초안 승인만으로 구현 시작·공유 서비스 배포가 완료된 것으로 기록하지 않는다.
