# 공식 Codex의 세션 유지 계정 전환 검증

- 작성일: 2026-09-15
- 이슈: UI-1dtr
- 상태: 설계 초안, 사용자 승인 전
- 경로: spec_backed — 하나의 검증 도구와 결과 보고서를 만드는 단위다.

## 목표와 성공의 의미

사용자는 공식 Codex를 계속 업데이트하면서, 실행 중인 작업을 끄거나
resume하지 않고 다음 모델 요청부터 다른 계정을 사용하기를 원한다.
이 작업은 로컬 프록시로 그 요구를 충족할 수 있는지 실증한다.
워커 연동을 먼저 구현하거나 가능하다고 가정하지 않는다.

성공은 **같은 Codex 프로세스와 대화에서, 진행 중인 요청과 도구 실행을
유지한 채 다음 요청의 실제 서버 인증 계정이 A에서 B로 바뀌는 것**이다.
프록시의 선택 로그만 바뀌거나 프로세스를 다시 띄운 결과는 성공이 아니다.
HTTP 연결 또는 서버 연결의 재생성 자체는 세션 재시작으로 세지 않는다.

결정: 공식 Codex와 CLIProxyAPI의 원본 코드는 수정하지 않는다 — 사용자의
업데이트 유지 요구를 지킨다. 설치된 전역 실행 파일·기본 로그인·공유 워커는
변경하지 않는다. 제품 UI와 운영 배포는 이 검증의 범위 밖이다.

## 확인한 근거

1. 현재 설치본은 공식 codex-cli 0.154.0이다. 버전은 실행 진입 시 다시 기록한다.
   워커는 `server/worker/runner/codex.js`에서 `codex exec --json`을 띄우며,
   계정은 `scheduler.js:resolveLaunchAccounts`에서 시작 전에 결정한다.
2. 공식 [사용자 지정 공급자 설정](https://developers.openai.com/codex/config-advanced#custom-model-providers)은
   요청 주소·Responses 형식·요청 헤더를 지정하는 경로를 제공한다.
   이는 프록시 접속 수단의 근거이며 계정 전환 성공의 증거는 아니다.
3. [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI#overview)는 Codex의
   구독 계정 로그인, 다중 계정, 도구 호출, 스트리밍을 지원한다고 명시한다.
4. 조사 기준 커밋은 `7bbfeaf8a7acf2cd5a834dcb0842539fe6aabc2b`다.
   [`sdk/pluginapi/types.go`](https://github.com/router-for-me/CLIProxyAPI/blob/7bbfeaf8a7acf2cd5a834dcb0842539fe6aabc2b/sdk/pluginapi/types.go)는
   `Scheduler.Pick`에 요청 헤더·metadata·후보 인증 목록을 전달하고 `AuthID`를
   돌려받는다. [`internal/pluginhost/scheduler.go`](https://github.com/router-for-me/CLIProxyAPI/blob/7bbfeaf8a7acf2cd5a834dcb0842539fe6aabc2b/internal/pluginhost/scheduler.go)는
   선택 ID가 후보 목록에 속하는지 확인한다. v6 설명서의 일반 embedding 경로와
   이 v7 플러그인 경로를 같은 API로 취급하지 않는다.
5. WebSocket 핸들러는 연결별 계정·이전 응답·도구 상태를 유지한다. 요청별
   선택 기능이 있어도 기존 연결의 계정 고정이 우선할 수 있다.
   이전 응답 참조, 암호화된 추론 항목, 압축된 대화가 계정을 넘을 때 유지되는지는
   확인되지 않았다. 과거 이슈 보고를 현재 버전의 확정 결함으로 단정하지 않는다.

## 대안과 선택

| 접근 | 판단 |
|---|---|
| 외부 프록시와 공식 확장점 | 검증 대상으로 선택. 원본 업데이트를 유지하면서 요청별 계정을 제어할 수 있다. 대화 연속성은 실증이 필요하다. |
| Codex 수정판에 실행 중 인증 재읽기 추가 | 사용자가 원본 수정·업데이트 추적 부담을 원하지 않아 제외한다. |
| 프로세스 종료와 자동 resume | 구현 가능한 다른 동작이지만 사용자가 요구한 전환을 충족하지 않아 제외한다. |

## 검증 구성

검증 도구는 `scripts/probes/codex-proxy-account-switch/` 아래에 둔다.
기존 Node.js 런타임으로 실행을 제어하고, 필요한 계정 선택 확장만 프록시의
공식 플러그인 SDK로 작성한다. SDK·도구 버전과 의존성을 검증 디렉터리에
명시하며 루트 런타임 의존성에는 추가하지 않는다.

| 구성 | 책임과 경계 |
|---|---|
| 실행 제어기 | 격리 디렉터리와 localhost 포트를 준비하고 공식 Codex를 한 번만 시작한다. 프로세스 신원·대화 ID·요청·도구 순서를 기록한다. |
| 계정 선택 플러그인 | 시험 실행의 불투명 식별자를 요청 헤더에서 받아 A/B 매핑을 읽고 허용된 정확한 인증 ID를 고른다. 다른 계정을 비활성화하거나 임의 계정에 위임하지 않는다. |
| 로컬 프록시 | 모델 요청과 응답을 중계한다. 운영 서버와 독립된 프로세스로 실행하며 외부 공개 주소에 바인딩하지 않는다. |
| 가짜 서버와 도구 | 실제 토큰 없이 스트림 중 전환, 후속 요청, 잘못된 선택, 다른 실행의 계정 불변을 결정적으로 확인한다. |
| 증거 수집기 | 요청 수신부터 실제 upstream 인증 선택·응답·도구 완료까지 연결한다. 비밀정보를 제거한 결과만 보고서에 기록한다. |

플러그인을 현재 공식 배포물에 로드할 수 있는지 먼저 확인한다. 조사한 소스에
인터페이스가 있다는 이유만으로 배포물 호환성을 가정하지 않는다. 해당 커밋을
빌드해야 한다면 원본을 수정하지 않은 격리 빌드만 허용하고 결과를 명시한다.
원본 패치 없이는 로드할 수 없으면 이 접근의 부적합 판정으로 끝낸다.

계정 선택 결과가 거부되거나 플러그인이 실패했을 때 내장 자동 선택으로
넘어가는지도 시험한다. 정확한 계정을 보장하지 못하면 upstream으로 보내지
않아야 한다. 공식 확장점으로 이 조건을 만들 수 없으면 통과시키지 않는다.

## 요청과 전환의 순서

1. 시험 실행 X의 계정은 A, 대조 실행 Y의 계정도 A로 시작한다.
2. X의 첫 모델 요청과 도구 실행이 확인된 뒤 X의 매핑만 B로 바꾼다.
3. 이미 시작한 응답은 A에서 끝난다. 실행 중인 도구를 취소·재실행하지 않는다.
4. X의 다음 모델 요청은 B, Y의 요청은 계속 A로 인증되어야 한다.
5. B가 이전 대화의 정보와 도구 결과를 사용해 작업을 마치는지 확인한다.
6. X의 프로세스 신원과 대화 ID가 같고, 새 `exec`·`resume`·`fork` 실행이나
   사용자 요청 재제출 없이 전환됐는지 확인한다.

매핑 변경은 로컬 제어기의 명시적 조작이다. 프록시의 기본 라운드로빈 선택이나
장애 후 우연한 failover를 전환 증거로 사용하지 않는다.

## 전송 방식과 대화 연속성

첫 검증은 공식 사용자 지정 공급자에서 제공하는 HTTP 스트리밍으로 수행한다.
출력을 조금씩 받는 동작과 도구 호출을 유지하면서 연결별 계정 고정의 영향을
분리하기 위한 선택이다. 설치 버전에서 그 구성이 유효한지도 기록한다.

WebSocket은 별도 결과로 기록한다. 같은 연결에서 전환 가능한지, 프록시가
계정을 고정하는지, 새 upstream 연결이 필요한지를 구별한다. HTTP만 통과하면
결과는 `supported_http_streaming`이며 모든 전송 방식이 지원된다고 쓰지 않는다.

다음 항목은 단순한 두 번의 텍스트 응답으로 대체할 수 없는 필수 검증이다.

- 이전 대화의 값과 완료된 도구 결과가 전환 뒤에도 유지된다.
- 존재하는 이전 응답 참조와 도구 호출 ID를 다른 계정에 전달할 때 정상적으로
  이어지거나, 프록시의 문서화된 변환으로 같은 의미가 보존된다.
- 추론 항목과 압축된 대화가 포함된 후속 요청도 정상적으로 이어진다.
- 실패한 요청을 재전송할 경우 이미 완료된 도구 부작용이 반복되지 않는다.

이전 응답 참조만 삭제하거나 새 대화를 시작해서 오류를 없앤 결과는 통과가
아니다. 자체 대화 복원 계층이 필요해지면 이 설계에서 임의로 확장하지 않고
필요한 입력·범위·관측 결과를 부적합 보고서에 적는다.

## 실계정과 비밀정보 경계

설계 승인은 계정 선택이나 로그인 변경의 승인이 아니다. 오프라인 검증 뒤,
실행 세션이 사용할 두 계정과 최대 요청 수를 사용자에게 제시하고 확인받는다.
실계정 검증은 두 계정에서 같은 모델을 사용할 수 있을 때만 진행한다.

첫 실험은 기존 계정의 짧은 수명 access token과 계정 식별자만 격리해 사용한다.
refresh token은 복사하지 않고 프록시에 토큰 갱신을 맡기지 않는다. 원본 인증
파일과 기본 로그인은 쓰지 않는다. 필요한 저장은 권한 0600의 시험 전용
임시 파일에 한정하며, 수명 종료 시 자신이 만든 파일만 제거한다.
공식 프록시 경로가 이 제한을 지원하지 않으면 실제 인증을 가져오기 전에
중단하고 필요한 인증 소유권 변경을 별도 설계한다.

실험에는 저장소 코드나 비공개 대화 대신 합성 프롬프트와 시험용 도구만 쓴다.
전체 모델 요청은 최대 12회로 제한하며 무한 자동 재시도·자동 계정 탐색은
사용하지 않는다. 토큰 만료나 인증 오류는 갱신 또는 다른 계정 대체로 숨기지
않고 해당 실행을 종료한다. stdout·stderr·요청 캡처·결과 파일에 토큰과 인증
헤더를 기록하지 않는다.

이 제한으로 토큰 갱신 중의 장시간 운용은 입증되지 않는다. 결과 보고서는
이를 생산 환경 연동 전의 명시적 미검증 조건으로 남긴다.

## 통과 기준과 산출물

단일 결과 보고서는 `docs/research/codex-proxy-account-switch/` 아래에 작성한다.
다음 관측을 표로 기록하고, 확인하지 못한 항목은 실패·미검증으로 구분한다.

- 공식 Codex 버전·실행 파일 식별값, 프록시 커밋·SDK·빌드 방식.
- 단일 프로세스 신원과 대화 ID의 전후 비교.
- X의 A→B 및 Y의 A 유지에 대한 실제 upstream 인증 선택 증거.
- 스트림 완료, 도구 호출·완료 횟수, 전환 뒤 대화·압축·추론 항목의 연속성.
- HTTP와 WebSocket 각각의 통과·미지원·미검증 결과.
- 인증 원본과 전역 설정의 비변경 확인 및 시험 자원 정리 결과.

결과는 `supported_http_streaming`, `supported_http_and_websocket`,
`unsupported` 중 하나로 적는다. 필요한 실계정 확인을 받지 못했거나 필수
연속성 검증을 수행하지 못했다면 `unverified`다. 오프라인 테스트만으로
실계정 전환 성공을 선언하지 않는다.

검증 도구의 로컬 테스트와 저장소 필수 검증을 수행한다. 실험에서 부적합이
확인돼도 정확한 결과 보고서와 재현 도구는 이 검증 단위의 유효한 산출물이다.
이 경우 계정 전환 기능을 완성했다고 보고하지 않는다.

## 경계·후속

실제 워커에 연결할 실행별 매핑, 설정 변경의 적용 범위, 적용 계정 이력,
사용량 한도 정책과 장기 토큰 갱신, 서비스 설치·배포는 검증 결과를 전제로
설계할 후속 작업이다. 현재 결과 없이 그 구현 구조나 저장소 분할을 확정하지
않는다. 이 문서는 운영 서비스 변경이나 후속 구현의 승인을 포함하지 않는다.

## 결정 (ADR 후보)

- 전제: ADR 0052 — 기존 자동 전환의 허용 계정·launch-only 정책을 운영 코드에서 변경하지 않는다. 검증은 별도 프로세스와 합성 작업에서 수행한다.
- 전제: ADR 0027 — 시험 보고서를 운영 Worker 이력으로 쓰지 않는다. 실제 연동의 계정 전환 이력은 후속 설계가 기존 타임라인 소유권에 맞춘다.
- 공식 Codex와 프록시 원본을 수정하지 않는 검증 경계 — 되돌리기 어려움: 아니오, 맥락 없이 놀라움: 아니오, 실제 절충: 있음; 생산 환경 구조를 아직 결정하지 않는 일회 검증 범위이므로 → ADR 아님.
