# 연결 레인 진행 — 기존 대기 위치 보존과 선행 자동 복귀 정합

- Bead: UI-tjus
- 작성일: 2026-09-08
- 상태: 작성안 — 구현 전 문구 확인 대상
- 경로: spec_backed, 한 저장소·한 구현 단위

## 1. 목표와 승인된 방향

사용자가 연결 레인의 진행을 눌러도 이미 놓인 이슈의 병렬·직렬 레인과 순번이
바뀌지 않는다. 선행 의존은 레인 소속과 무관하게 구현 착수를 막고, 선행이 해소되면
기존 실행 권한·직렬 순서·점유 조건에 따라 원래 자리에서 자동 실행을 다시 판단한다.
연결 레인 없이 상세에서 선행을 지정한 이슈도 같은 대기·복귀 경로를 탄다.

2026-09-08 대화에서 사용자는 별도 크로스레포 직렬 레인 대신 위 동작을 요청했고,
기존 배치 보존·선행 대기 공통화·관련 문서와 코드 정합 방향에 대해 수정을 지시했다.

## 2. 확인한 원인과 계약 소유권

- ADR 0034는 연결 레인 소속이 아닌 선행 의존을 기준으로 대기와 이벤트 기반 복귀를
  정의한다. 새 복귀 상태나 주기 조회기를 추가할 요구가 아니다.
- ADR 0035는 진행 시 직렬 멤버도 병렬 큐로 옮기도록 정했다. Monitor의 `runLane`은
  `queue_index`가 없는 비고정 행에 병렬 `worker-queue-place`를 보내 이 결정을 구현한다.
- 현재 진행 권한은 병렬 대기·PR 대기 행에 적용된다. 이동만 제거하면 자동 진행이 꺼진
  워크스페이스에서 직렬 멤버가 진행 권한을 받지 못하므로 두 표면을 함께 맞춰야 한다.
- 화면의 `armed_by_bead`는 병렬·PR 대기만 읽는다. 직렬 행도 권한을 읽어야 연결 레인
  진행 상태와 해제 조작이 실제 실행 상태와 일치한다.
- 실행 권한 필드 `armed_by_lane`은 이 저장소의 큐 상태와 메시지 계약이 소유한다.
  dotfiles의 공통 workflow 계약·라벨·Bead 완료 상태 의미는 이번에 바꾸지 않는다.
- 정본: 이 설계 승인 후 이를 가리키는 새 ADR로 ADR 0035를 supersede한다.
  활성 소비자는 Monitor 진행, 큐 저장소, 스케줄러, 공통 레인 모델, 메시지 문서다.
  배포용 생성물은 `app/main.bundle.js`와 `app/main.bundle.js.map`이다.
  서버 메시지 핸들러의 병렬 전용 주석도 새 의미로 맞추고, payload나 핸들러 분기는
  바꾸지 않는다. 새 ADR은 ADR 0035의 살아 있는 확정·진행 분리와 소유한 권한만
  해제하는 조항을 함께 재기록한다. 과거 ADR 본문의 결정을 덧고치지 않는다.

### 현재 코드 근거

- Monitor 이동: `app/views/monitor/index.js`의 `runLane`.
- 권한 저장·해제: `server/worker/queue-store.js`의 `arm`, `disarm`, `disarmEntry`,
  `ensureLoaded`, `place`, `setSerialLaneCount`, `moveToPrWait`.
- 직렬 발차: `server/worker/scheduler.js`의 `startNowSerialHeads`, `armedByLaneOf`,
  실행 패스의 early return 및 직렬 선두 후보 생성.
- 선행 복귀: 같은 파일의 `runWaitingRescan`과 `server/worker/attach.js`의
  `holdsWaitingOn` 및 외부 workspace activity 구독. 복귀는 기존 코드로 충족한다.
- 화면 권한 집계: `app/views/worker/lane-model.js`의 `armed_by_bead` 구성.

## 3. 결정

### 3.1 진행은 기존 위치를 보존한다

- 이미 병렬 또는 직렬 대기 영역에 있는 멤버는 이동·재삽입·재정렬하지 않는다.
  레인 ID, 순번, 대기 진입 시각을 유지한다.
- 아직 어느 대기 영역에도 없는 멤버만 자기 저장소 병렬 큐 끝에 적재한다.
- 실행중·PR 대기·완료 행에는 적재하지 않는다.
- 적재가 필요한 행의 적재를 끝낸 뒤 저장소별로 기존 진행 권한 요청을 보낸다.
  현재의 응답 revision 연결과 부분 실패 처리·이어서 진행 재클릭을 유지한다.
- 저장소 전체의 자동 진행·자동 머지 설정은 바꾸지 않는다.

### 3.2 기존 진행 권한을 직렬 대기 행에도 적용한다

- `worker-queue-arm`과 `worker-queue-disarm`의 메시지와 필드를 유지하고 적용 대상을
  병렬·직렬·기존 PR 대기 행의 합집합으로 맞춘다. 별도 직렬 권한 필드는 만들지 않는다.
- 기존 revision 일치 검사와 중복 요청의 no-op 의미를 유지한다.
- 요청에 든 대상 멤버만 권한을 얻는다. 이 합집합 밖 ID는 기존대로 무시하고 다른 연결 레인의
  권한을 해제하지 않는다.
- 직렬 진행은 그 레인의 선두에 도달한 멤버만 실행 후보로 만들 수 있다. 뒤에 있는
  armed 멤버 때문에 앞의 unarmed 이슈를 자동 실행하거나 건너뛰지 않는다.
- 선두가 선행 대기 중이면 그 직렬 레인은 기다린다. 다른 병렬 이슈·다른 직렬 레인은
  자신의 실행 조건이 맞으면 계속 진행한다. 실행 세션과 실행 슬롯을 대기용으로 쓰지 않는다.
- 선행 의존, 실행 자격, 일시정지, 실행 슬롯 및 직렬 점유 검사는 기존 판정에 남는다.
  진행 권한은 이 조건을 우회하지 않는다.
- 정지·연결 레인 이탈·삭제는 만든 진행 권한만 해제한다. 이미 실행 중인 세션이나
  머지 권한을 취소하지 않고 대기 위치도 바꾸지 않는다.
- 저장 정규화는 기존 비어 있지 않은 문자열 규칙을 그대로 쓴다. 서버의 cold load는
  병렬·직렬·PR 대기의 권한을 모두 지우고 해제된 레인 목록을 기존 일회성 표시로 보낸다.
  재시작에 대한 새 자동 재승인이나 별도 복구 상태는 도입하지 않는다.
- 실행 시작 시 직렬 대기 행의 권한도 attempt snapshot에 싣는다. 실패 시 이슈 하나의
  권한 해제가 직렬 행에도 적용되고, 해당 실패가 다른 멤버 권한을 지우지 않는다.
- 사용자의 명시적 place는 기존대로 새 대기 entry를 만들므로 권한을 지운다. 단순 순서
  변경은 entry를 보존하고, 직렬 레인 수 축소로 병렬 끝에 옮겨지는 행도 기존 entry와
  권한을 보존한다. 이번 진행 조작 자체는 이미 놓인 행에 place를 호출하지 않는다.
- attempt를 통한 PR 대기 이동과 재시작 해제 후 권한 재식재 방지는 기존대로 유지한다.
  외부 PR 관측 경로의 권한 전파 방식은 바꾸지 않는다.

### 3.3 대기와 복귀는 기존 공통 경로를 유지한다

- 미해결 선행이 확인되면 기존 `prerequisite_unmet` 진단과 선행 목록을 사용한다.
- 선행 저장소의 변경 이벤트 또는 기존 시작 시 재스캔에서 후행의 실행 가능 여부를
  다시 읽고, 준비된 경우 기존 실행 패스로 보낸다. 연결 레인 ID를 복귀 필수 조건으로
  삼지 않는다.
- 실제 세션이 떴다가 선행 미충족으로 정상 종료한 `waiting` 결과와 실행 전 대기
  항목의 복귀를 모두 보존한다.
- 이슈를 만들기만 했거나 대기열 밖에 둔 경우까지 자동 적재·실행하지 않는다.
- 선행 완료 의미는 기존 Beads readiness 판정이 소유한다. PR 생성·코드 작성만으로
  선행이 완료됐다고 새로 추정하지 않는다.

### 3.4 화면은 같은 저장 상태를 읽는다

- 공통 레인 모델은 병렬·직렬·PR 대기에서 진행 권한을 읽는다.
- 직렬 멤버도 연결 레인 헤더의 진행 중·미발차 집계와 기존 진행 권한 칩에 반영한다.
  새 버튼·배지·카드 슬롯은 만들지 않는다.
- 권한 해제나 재시작 후 표시는 현재 규칙대로 되돌아간다. 사라진 연결 레인의 권한도
  기존 고아 권한 표시와 해제 조작으로 확인할 수 있어야 한다.

## 4. 검토한 대안

1. 현행 병렬 이동 유지: 서버 권한 처리는 단순하지만 사용자가 고른 직렬 배치가 깨진다.
2. 이동만 제거: diff는 작지만 자동 진행이 꺼졌을 때 직렬 멤버의 진행이 성립하지 않는다.
3. 기존 권한의 적용 대상을 직렬까지 맞추고 위치 보존: 저장·선택·표시를 함께 고쳐야
   하지만 새로운 상태나 실행 레인을 만들지 않고 요청한 동작을 충족한다. 채택한다.

## 5. 검증과 인수 기준

- Monitor: 혼합 연결 레인에서 병렬·직렬 멤버는 place 요청을 받지 않고 미적재 멤버만
  병렬 끝에 추가된다. 진행 권한 요청은 해당 저장소들에 전달된다.
- 큐 저장소: 병렬·직렬 멤버의 권한 부여·해제, ID 제한, 무관한 레인 권한 보존,
  중복 호출, 저장·재시작 및 수동 이동 규칙을 검증한다.
- 스케줄러: 자동 진행이 꺼져도 armed 직렬 선두는 실행하고 unarmed 선두와 직렬
  후순위는 실행하지 않는다. 선행 차단과 점유 중인 레인은 여전히 실행하지 않는다.
- 선행 복귀: 연결 레인 없이 다른 저장소 선행을 가진 병렬·직렬 후행 각각이
  선행 미충족 동안 발차하지 않으며 선행 완료 이벤트 뒤 실행 조건에 맞게 시작한다.
  직렬 후순위는 선행이 풀려도 자기 차례까지 기다린다.
- 화면: 직렬 권한이 진행 중·미발차 집계와 기존 칩에 반영되고 해제하면 사라진다.
- 기존 대기·복귀 테스트에서 실제 공백이 확인되면 같은 소유 경로의 최소 수정으로
  닫는다. 다른 원인이나 새로운 상태 기계가 필요하면 근거를 가지고 설계를 재판단한다.
  현재 조사에서는 scheduler의 복귀 후보가 이미 병렬·직렬 합집합이며 attach의 외부
  이벤트 매칭도 선행 목록을 읽는다. 이 둘의 복귀 로직 변경은 필요하지 않다.
- 구현 검증 전에 해당 checkout의 Node 버전(>=22)과 `npm ls --depth=0`를 확인한다.
- 전체 검증: `npm run tsc`, `npx vitest run --reporter=dot`(120초 상한),
  `npm run lint`, `npm run prettier:write`, `npm run build`.
  포맷 명령이 무관한 파일을 바꾸지 않도록 root가 전체 diff를 확인한다.
- ADR 인덱스 생성·검사와 활성 인용 검사를 통과시키고 빌드 결과 두 파일을 포함한다.
- PR 인도와 실제 배포 완료는 구분한다. 머지·배포 단계에서는 선언된 배포 작업 성공,
  merged SHA의 공유 서비스 프로세스 경로·포트·HTTP 응답까지 확인한다.

## 6. 경계

- 별도 크로스레포 직렬 레인, 연결 레인 필수 가입, 새로운 실행 플래그·상태,
  주기 조회기, 자동 재시도 계층, 새 의존 판정자는 만들지 않는다.
- 연결 레인 확정·재적용은 기존대로 의존만 편집한다. 큐 적재는 진행 조작이 맡는다.
- 직렬 순서 자체를 바꾸거나 선두를 우회하지 않는다. 연결 레인 전체 삭제나 UI 재설계는
  범위에 넣지 않는다.
- 추가 의존성 패키지는 필요하지 않다. 한 구현 단위에서 root가 전체 diff와 검증을
  확인한다.

## 결정 (ADR 후보)

- 전제: ADR 0034 — 선행 대기와 자동 복귀는 연결 레인 소속과 무관한 기존 이벤트 경로를 따른다.
- 전제: ADR 0035 — 확정·재적용은 의존만 쓰고 진행이 적재와 권한을 쓰는 분리는 승계한다.
  직렬 멤버를 병렬로 옮기는 조항은 이번 설계로 대체한다.
- 전제: ADR 0011 — 저장소 자동 진행과 자동 머지 스위치를 독립적으로 유지한다.
- 전제: ADR 0014 — 공통 레인 모델과 기존 카드 슬롯으로 표시한다.
- 연결 레인 진행은 기존 병렬·직렬 위치를 보존하고 같은 진행 권한을 두 대기 영역에
  적용한다. 되돌리기 어려움: 저장·실행·표시 소비자를 함께 바꿔야 한다. 맥락 없이
  놀라움: 연결 레인 진행이 저장소 자동 진행을 켜지 않고 직렬 순서도 우회하지 않는다.
  실재한 대안: 현행 병렬 이동 또는 이동만 제거하는 선택과 비교했다.
  `summary`: "연결 레인 확정은 의존만 쓰고 진행은 기존 병렬·직렬 위치를 보존하며 같은 진행 권한을 적용한다"
  → ADR, supersede 0035
