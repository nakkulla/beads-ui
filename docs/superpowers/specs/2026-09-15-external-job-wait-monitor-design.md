# 모니터의 외부 계산 대기와 자동 감시 상태 표시

- 개선 이슈: UI-7341
- 작성: 2026-09-15
- 상태: 사용자 검토용 초안, 구현 미착수
- 조사 기준: `origin/main`의 `462906256d9bebbde52c1f87cecd226f861645e1`
- 실행 경로: `spec_backed`. 한 저장소의 데이터 수집·공용 표시·상세 탐색을 한
  구현 및 검증 묶음으로 완료한다.

## 1. 요구와 확인한 원인

사용자는 존재를 알 수 없는 이슈가 선행으로 표시되는 문제를 지적했고, 실제 계산
종료 감시가 동작하는지 확인하며 Monitor에서도 대기 항목과 상태를 볼 수 있게
요청했다.

원래 작업 Analysis-xz9d의 선행 Analysis-ph3a·Analysis-5dbb는 외부 계산 작업
246416·246417의 종료를 기다리는 실제 `gate`(대기 조건 이슈)다. 2026-09-15
04:51·04:53 KST에 자동 생성됐다. 일반 `bd list --all --limit 0 --json`에서는
제외되고 `--include-gates`를 붙이면 `issue_type`, `await_id`, `await_type`을
포함해 조회된다.

`server/workspace-snapshot-coordinator.js`의 목록 명령에 이 옵션이 없어서 대기
이슈가 스냅샷의 `id_index`(상세 조회 인덱스)에 없다. `compactDependency`는
대상이 없을 때 빈 제목과 ID만 반환하며, 상세 역시 같은 인덱스를 사용하므로
클릭해도 대상을 찾지 못한다. 감시 기록도 현재 Monitor에 전달되지 않는다.

감시 자체는 다음과 같이 확인했다.

- 06:03 KST 원격 조회: 두 작업 모두 `PENDING`, 사유 `Priority`로 실행 순번 대기.
  05:54 관측 기록과 일치했다.
- 자동 실행 서비스: 900초 간격, 25회 실행, 마지막 종료 코드 0. 최근 네 주기 모두
  오류 0이며 별도 오류 로그도 비어 있다.
- 작업 종료 이력 조회인 `sacct`는 서버에서 비활성화돼 있지만 감시 구현은 이에
  의존하지 않는다. 현재 작업 정보 또는 해당 실행의 마지막 시작·종료 로그와 종료
  코드로 판정한다.
- 실제 두 실행 스크립트는 작업 번호와 시작·종료·종료 코드를 남긴다. 배포된 감시
  구현과 검사한 정본 파일의 SHA-256이 같고, 기존 감시 테스트 58개가 통과했다.
- 조사 중 06:09 KST의 다음 자동 주기도 직접 확인했다. 두 watch의 마지막 관측이
  06:09:09·06:09:10으로 전진했고 오류 0, 다음 확인은 06:24로 기록됐다.
- 이 두 실제 작업은 아직 끝나지 않았다. 이 실행들의 자동 해제까지 검증했다고
  주장하지 않는다. 강제 중단 뒤 종료 기록까지 사라지면 확인 불가로 남는 한계가
  있다.

## 2. 선택한 방식과 대안

사용자가 자동으로 기다리는 일을 직접 해결해야 할 일로 오해하지 않도록, **기존
Monitor의 대기 영역에 외부 작업 행을 표시하고 원래 이슈·감시 상태·확인 시각을
함께 보여 준다.** 누락된 gate는 기존 스냅샷에서 함께 읽어 상세 접근도 복구한다.

- 원래 이슈에 설명 칩만 붙이면 변경은 작지만, 실행 시도나 큐 항목이 없을 때
  대기를 찾지 못하므로 충분하지 않다.
- 별도 전역 탭이나 새 실행 대기열은 같은 대기를 두 군데에서 관리하게 만든다.
  기존 대기 영역에 읽기 전용 관측 행을 넣는다.
- gate를 일반 실행 후보로 섞으면 실행할 일이 없는 시스템 항목에 실행·배치 조작이
  생긴다. 상세 데이터에는 포함하되 실행 후보·큐 멤버십과 분리한다.

행과 상세는 현재 공용 레인 모델·렌더러와 기존 상세 오버레이를 사용한다. 새
스케줄러, 원격 조회 루프, 수동 gate 해제 기능은 만들지 않는다.

## 3. 원본과 읽기 경계

### 3.1 이슈 스냅샷

정상 스냅샷의 `ALL_ARGS`에 `--include-gates`를 추가한다. 원래
`--all --limit 0`과 원자적 세대 판정은 유지하며, 기본 bd 조회는 여전히 목록·실행
가능 사유의 2회다. gate별 `bd show`, DB 직결, 상세 전용 조회는 추가하지 않는다.

정규화는 gate의 `issue_type`, `await_id`, `await_type`을 보존한다. 모든
이슈·간선 인덱스에 gate가 있으므로 기존 상세와 선행·후속 제목 조회가 같은
세대에서 성립한다.

일반 Board 목록, 실행 후보, 직접 세션 후보, Worker 큐 후보 투영에서는
`issue_type=gate`를 제외해 기존 일반 목록 범위를 보존한다. gate 전용 상세와 아래
관측 행은 인덱스에서 읽는다. `ready`·admission 판정은 bd/기존 Worker가 소유하며,
표시용 행을 그 입력에 넣지 않는다. 미지원 CLI의 옵션 오류를 gate 없는 성공으로
숨기지 않고 기존 스냅샷 오류로 표시한다.

### 3.2 감시 기록

정본은 dotfiles의 `docs/contracts/external-job-monitor.md`이며,
`external-job-monitor-v1`(외부 작업 감시 기록 형식)을 그대로 소비한다.
런타임에서 dotfiles 체크아웃이나 계약 문서를 읽지 않는다.

새 `server/external-job-observations.js`는 서버의
`XDG_STATE_HOME/bead-job-monitor`, 미설정 시 홈 디렉터리의
`.local/state/bead-job-monitor` 아래 `watches/*.json`을 비동기로 읽는다.
지원하는 현재 배포도 이 기본 루트를 사용한다. 감시기의 별도 `--state-dir`은 자동
탐색하지 않으며, 해당 기록을 찾지 못하면 자동 감시라고 추정하지 않고 정보
없음으로 표시한다.

전체 서비스를 실제로 조회하는 읽기 전용 명령 `bead-job-monitor show --service`를
비동기로 실행하여 서비스 등록·명령 일치·최근 실행 결과를 얻는다. watch마다
실행하지 않고 갱신 주기당 서비스 전체에 한 번 공유한다. 이 명령의 `ok`는 서비스
설정 조회 결과이며, 개별 작업의 성공 또는 매번 관측했다는 뜻으로 바꾸지 않는다.

기존 Monitor 구독 시작과 `createRunnableRefreshDriver`의 주기 갱신에 수집을
결합한다. 새 타이머를 만들지 않고 중첩 수집은 하나의 진행 중 요청을 공유한다.
수집 완료 뒤 기존 `schedulePush`를 호출한다. 구독 해제·서버 종료에서 관련 자원을
정리하고, 동기 투영 함수에서는 파일 읽기나 자식 프로세스를 실행하지 않는다.
설정상 폴링 0이면 최초 수집과 기존 명시적 갱신만 수행하고, 화면의 시각은 실제
마지막 수집 시각으로 남긴다.

### 3.3 저장소 대응과 실패 표시

watch의 `repo`는 일반 저장소가 아니라 작업 체크아웃일 수 있다. 이미 보이는
저장소 목록과 해당 저장소의 실제 Git common directory를 기준으로 연결한다.
문자열 접두사나 이슈 ID 접두사만으로 프로젝트를 결정하지 않는다. 같은 체크아웃의
경로 해석은 한 수집 안에서 공유한다.

자동 관리 gate로 연결하려면 다음이 모두 맞아야 한다.

1. 지원 스키마와 유효한 watch ID.
2. 실제 같은 저장소의 `gate_id`와 `issue_type=gate`.
3. gate의 `await_id=watch_id`, `await_type=human`.
4. 동일 스냅샷에서 `consumer → gate_id`인 실제 `blocks` 관계와 원래 이슈.

확인된 관계만 표시하며 원격 경로·Worker API URL을 연결 조회에 실행하거나
사용하지 않는다. 삭제된 체크아웃 등으로 저장소를 확정할 수 없으면 그 watch를
임의 프로젝트에 붙이지 않는다. 해당 저장소의 실제 열린 gate는 정보 없음 행으로
남으므로 조용히 사라지지 않는다. 숨긴 저장소는 Monitor 관측 행 목록에 노출하지
않는다.

파일 하나가 깨져도 다른 정상 항목을 버리지 않는다. 최초 로딩, 수집 실패, 미지원
스키마, 잘못된 관계는 각각 정보 조회 중 또는 감시 정보 확인 필요로 표시한다.
이전 정상 자료를 유지할 때는 오래된 자료임을 함께 표시하고 정상 감시로 표시하지
않는다. 원본이 없는 이유를 임의로 생성하지 않는다. gate 존재·open/closed는 이슈
스냅샷, 작업 관측은 watch가 소유한다.

## 4. Monitor의 표시

### 4.1 대기 영역의 외부 작업 행

기존 대기 영역에 접을 수 있는 **외부 작업·대기 조건** 묶음을 더한다. 같은
`buildLanes`가 만든 읽기 전용 행을 공유 `waitBody`·`miniRow`로 그린다. 별도
탭이나 실행 레인은 아니다. 저장소 이름·원래 이슈·gate ID 순으로 정렬하며 각 행에
저장소 배지를 둔다.

열린 native gate는 감시 기록이 없어도 `대기 조건 · 감시 정보 없음`으로 표시한다.
이 경우 사람이 승인해야 한다거나 자동 감시 중이라고 단정하지 않는다. 검증된 외부
감시 gate에는 아래 작업 상태와 감시 상태를 표시한다. 큐·실행 시도가 없어도 행과
저장소가 보이도록 `hasPipeline` 및 관련 개수 집계에 이 관측 집합을 포함한다.

외부 작업이 실행 중이어도 원래 이슈는 그 결과를 기다리므로 이 묶음에 남으며
`계산 중`으로 표시한다. Worker 실행 슬롯이나 작업 개수에는 가산하지 않는다.
드래그, 순서 변경, 큐 제거, 지금 시작, 재시도, gate 닫기 조작이 없는 관측
행이다.

최소 행 예:

```text
Analysis-5dbb · 외부 계산 · 실행 대기
외부 작업 246417 관측
자동 확인 중 · 마지막 확인 05:54 · 다음 확인 06:09
원래 이슈 Analysis-xz9d · microbiome_bile
```

열린 gate 또는 완료되지 않은 감시 기록은 계속 표시한다. gate가 닫히고 watch도
`complete`가 되면 7일 동안 같은 묶음의 **종료 확인** 접기 목록에 남기고 기본
열린 대기 수에서는 제외한다. 기준 시각은 실제 `completed_at`이며, 없으면 확정된
gate `closed_at`만 사용한다. 시간이 없으면 최근 종료라고 추정하지 않는다. 이
기록은 Worker 성공/완료 건수로 세지 않는다.

### 4.2 두 상태를 구분한다

작업 상태는 실제 watch 관측을 설명한다.

| 관측                                                        | 화면                       |
| ----------------------------------------------------------- | -------------------------- |
| `PENDING`                                                   | 실행 대기                  |
| `RUNNING`                                                   | 계산 중                    |
| `UNKNOWN` 또는 현재 결과 부재                               | 계산 상태 확인 필요        |
| 확정된 정상 종료, 산출물 존재                               | 종료 확인 · 결과 검증 필요 |
| 확정된 비정상 종료·취소·산출물 누락, `recovery_needed=true` | 종료 확인 · 조치 필요      |

감시 상태는 별도로 표시한다.

- `active`이고 관측·서비스 조회가 유효하면 `자동 확인 중`. 항상 실제 마지막·다음
  확인 시각을 함께 보여 준다.
- `preparing`, `gate_ready`, `handoff_incomplete`는 `감시 등록 확인 필요`.
- `terminal_recorded`, `gate_noted`는 `종료 확인 · 대기 해제 확인 중`. 실제
  gate가 아직 열려 있음을 유지하며, 원래 세션 종료가 원인이라고 추측하지 않는다.
- `stopped`는 `자동 확인 중지`. 계산 취소나 대기 해제를 뜻하지 않는다.
- 개별 `last_error`, 서비스 조회 실패·미등록·명령 불일치, 자료 읽기 실패는
  `감시 확인 필요`와 확인된 사유. 이미 아는 마지막 계산 상태는 그 관측 시각과
  함께 보존한다.
- 다음 확인 시각을 넘었으면 `자동 확인 중` 대신 `확인 예정 시각 지남`을
  표시한다. 이 사실만으로 계산 실패나 서비스 중단이라고 단정하지 않는다. 이미
  구체적인 오류/중지 사유가 있다면 그 사유를 우선하고 시각 경과를 덧붙인다.
- 서비스 한 번의 `last_tick.exit_code=0` 또는 `skipped=true`만으로 개별 작업을
  관측했다고 표시하지 않는다. 개별 시각과 오류가 기준이며 정상적인 주기 사이
  `loaded_state=not running`은 감시 중단으로 표시하지 않는다.

관측·시각 필드가 없으면 그 필드만 생략하고 정보 없음 사유는 남긴다. 모든 상태
전이는 표시 전용이며 이슈 status나 Worker admission을 쓰지 않는다. 전체
상태/스키마를 모르는 구버전 응답은 정상 완료로 강등하지 않는다.

### 4.3 상세와 원래 이슈 연결

gate ID·제목을 누르면 기존 상세 오버레이가 같은 저장소 스냅샷의 gate를 연다.
선행 ID를 다른 이슈로 몰래 바꾸거나 클릭을 원래 이슈로 우회하지 않는다. 별도
`원래 이슈 <ID>` 링크가 소비자 상세를 연다.

gate 상세 상단에 `대기 조건`을 명시한다. 자동 감시 연결이 검증된 경우
`외부 작업의 종료를 시스템이 확인합니다. 직접 닫을 필요가 없습니다.`와 작업
상태, 감시 상태, 마지막·다음 확인, 해제 조건을 표시한다. 자료가 없으면 자동
관리로 단정하지 않고 실제 gate 본문과 조회 한계를 보여 준다.

gate 상세는 읽기 전용이다. 일반 구현 설정·큐 배치·상태 변경·의존 편집을 노출하지
않는다. 감시 오류가 있을 때도 실제 원래 이슈와 확인된 오류를 안내하며 존재하지
않는 자동 복구 버튼은 만들지 않는다. 표시용 감시 자료는 현재 Monitor 스냅샷을
기존 상세 옵션/저장소 경로로 전달하고, 상세 열기 때문에 원격 SSH 또는 gate별 bd
조회를 추가하지 않는다. Monitor 자료가 없는 진입에서도 gate의 종류와 원문은
보여야 한다.

원래 이슈 카드에는 같은 저장소·실제 blocks로 연결된 미해제 외부 작업 수가 있을
때 **외부 계산 대기 N건** 판정 칩을 의존 줄에 표시한다. 클릭하면 작업별 상태와
원래 gate 상세 링크를 연다. 기존 `⛓ <ID>` 칩은 실제 gate 상세를 여는 의미를
유지하고 제목도 채워진다.

## 5. 공용 슬롯과 전달 자료

외부 작업 행은 기존 `LaneGate`(자동 디스패치 보류 자료)를 재사용하지 않는다.
`external_wait`라는 표시 전용 자료와 명시적인 관측 행 종류를 사용하며 기존
큐/재개 조작 분기로 들어가지 않는다.

`monitor-pipeline-snapshot.workspaces[]`에 선택적 `external_waits` 배열을
추가하고, `workspaces_state[]`의 해당 저장소 요약에는 대기 수·감시 확인 필요
수를 선택적으로 전달한다. `app/protocol.md`·형식 검사·store·공용 레인 모델을
함께 갱신한다. 자료가 없는 이전 서버에서는 기존 화면을 유지한다.

wire에는 확인된 프로젝트·gate·원래 이슈 identity, 화면에 필요한 관측/종료/서비스
상태와 시각·짧은 오류만 보낸다. 전체 watch JSON, SSH 설정, Worker API 주소, PID,
원격 로그 내용, 산출물 내용은 보내지 않는다. HTML은 기존 escaping 경로를
사용한다.

구현 전에 카드 문법 정본 §2·§5.1과 칩 문법 정본에 다음 슬롯을 반영한다.

| 요소                              | 자리와 의미                                      |
| --------------------------------- | ------------------------------------------------ |
| 외부 작업 종류·작업 상태          | 슬롯 1: 무엇이고 어떤 상태인지                   |
| 작업 제목                         | 슬롯 2                                           |
| 감시 상태·확인된 오류 요약        | 슬롯 3: 관측 진행                                |
| 원래 이슈 링크·외부 계산 대기 N건 | 슬롯 4a: 지금 기다리는 관계, 요약 칩은 사유 팝업 |
| 저장소 배지·원격 작업 번호        | 슬롯 5: 실행 위치/식별                           |
| 실제 마지막·다음 확인·종료 시각   | 슬롯 7                                           |
| gate ID·기존 의존 ID 클릭         | 기존 이슈 상세 열기 유지                         |

행의 읽기 전용 성격은 서버 실행 권한을 대체하는 장치가 아니다. 관측 배열은 큐
멤버십·attempt·자동 진행 설정을 만들거나 변경하지 않는다.

## 6. 검증과 수용 기준

구현 전 승인된 범위에서 필요한 실패 재현을 확정하고, 아래 동작을 기존 테스트에
추가한다. 임의의 실작업 종료·취소로 검증하지 않는다.

1. 일반 목록에서 빠진 두 gate를 `--include-gates`로 포함한 실제 모양의 fixture로
   같은 스냅샷 상세·제목·양방향 관계를 검증한다. 기본 bd 호출 2회와 legacy 3회,
   실패 시 원자성은 유지한다.
2. gate가 일반 Board·실행 후보·큐 배치 대상으로 흘러가지 않으며 원래 일반 이슈
   집합이 그대로다.
3. watch의 작업 체크아웃을 실제 Git common directory로 같은 저장소에 연결한다.
   접두사만 같은 다른 저장소, 같은 ID의 다른 rig, 잘못된 await ID/blocks, 숨긴
   저장소, 사라진 체크아웃은 잘못 연결하지 않는다.
4. 큐와 실행 시도가 전혀 없어도 열린 gate가 Monitor 대기 영역에 보인다. gate ID
   클릭은 상세를, 원래 이슈 링크는 소비자 상세를 연다.
5. 실행 대기·계산 중·확인 불가·정상 종료·취소/실패·누락 산출물·해제
   진행·중지·부분 등록·서비스 오류를 표대로 표시한다. 서비스 idle과 lock skip을
   작업 실패로 오인하지 않는다.
6. 다음 확인 시각 경과와 오래된 캐시를 표시하며, 파일 손상 하나가 다른 행을
   지우지 않는다. 부재/오류 뒤 복구되면 다음 수집으로 갱신한다. 초기 로딩도
   성공으로 표시하지 않는다.
7. 외부 행과 gate 상세에 드래그/시작/재시도/닫기/배치/편집 조작이 없고, 표시나
   클릭이 상태 쓰기·SSH·새 감시 등록을 호출하지 않는다.
8. 실제 gate가 닫혀야 미해제 관계가 사라진다. `complete`와 gate 상태가 어긋나면
   확인 필요로 남고, 종료 확인 이력은 7일 규칙에 따라 보이며 소비자 완료나 자동
   재개를 주장하지 않는다.
9. 여러 구독자가 있어도 주기당 수집을 공유하고 동기 투영에 파일 I/O·프로세스
   실행이 없다. 구독이 없으면 수집하지 않으며 정상 자료/이슈가 전혀 없는 환경은
   새 빈 영역을 그리지 않는다.
10. 390px 폭과 데스크톱 브라우저에서 작업 종류·대기 상태·확인 시각을 hover 없이
    읽을 수 있고, 원래 이슈/대기 상세 이동과 키보드 조작을 확인한다.

관련 검증 파일은 스냅샷·목록 어댑터·새 감시 수집기·Monitor 채널, 공용 레인
모델/렌더러, Monitor 화면·상세·프로토콜 테스트와
`app/main.monitor.e2e.test.js`다. source owner의 스키마/필드와 소비 subset의
대응도 검사한다.

최종 코드 검증은 저장소 규칙의 Node/의존성 확인, `npm run tsc`, `npm run lint`,
변경 파일 Prettier, `npx vitest run --reporter=dot` 전체 실행(120초 제한)이다.
`npm run build` 후 별도 로컬 화면에서 검증한다. 이 설계 초안 자체는 아직 코드
변경이나 배포 증거가 아니다.

## 7. 경계·후속

요청한 표시는 beads-ui 한 작업에 포함한다. dotfiles의 감시 판정·900초 주기·오류
재시도·gate 해제 순서, 원격 계산 자원·실행 순서·취소 정책은 변경하지 않는다.
승인된 기존 감시 계약과 실제 기록만 소비하므로 다른 저장소의 선행 변경은
필요하지 않다.

원격 종료 기록이 없는 경우를 성공으로 추측하거나 일반 gate의 human 표기를 사람
승인 요청으로 단정하지 않는다. 감시 종료는 결과 전달이며 소비자 구현 성공·자동
재개 보장이 아니라는 기존 경계를 유지한다.

실제 두 계산의 종료는 향후 실행 결과로 확인해야 한다. 현재 검증은 감시 가동·현재
상태 일치·종료 판정 코드/회귀 테스트까지다. 별도 형제 작업, Worker 배치, 원격
작업 변경은 이 초안에서 만들지 않는다.
