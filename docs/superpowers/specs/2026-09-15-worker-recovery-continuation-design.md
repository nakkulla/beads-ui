# 워커의 복구 가능한 오류 보존과 같은 단계 재개

- Bead: UI-3vvi
- 상태: 사용자 검토용 초안
- 근거 기준: beads-ui `93d7189bb7e5461415519c39a61d08b455322fc7`
- 정본·형제: dotfiles-9z2u, `docs/superpowers/specs/2026-09-15-recoverable-error-continuation-design.md`
- 적용 범위: Worker에 등록된 모든 저장소의 실행·복구·표시

## 문제와 목표

현재 Worker는 정상 종료 후 PR·정상 결과 줄이 없는 경우를
`session_ended_unresolved`로 처리한다. dotfiles-oeo1의 실제 오류는 구조화된
`error`와 `turn.failed` 안의 “You've hit your usage limit.” 안내였지만,
공급자 오류 분류기가 이 평문 형식을 인식하지 못해 일반 실패가 됐다.
원래 작업은 구현 후보와 검증이 남아 있고 중단된 리뷰부터 이어갈 수 있다.

Analysis-hkit는 형식 오류를 고칠 수 있는데도 세션이 종료됐다. 형식 오류 자체와
발행 호출 지침의 직접 수정은 dotfiles-9z2u가 맡고, Worker는 이미 끝난 실행의
미완료 작업을 무조건 실패로 종단하지 않도록 바꾼다.

목표는 실제 오류 증거를 보존하면서 원인에 맞춰 수정·대기·같은 단계 재개를 수행하는
것이다. 프로세스 종료와 원시 operation 실패는 사실로 남긴다. 현재 작업을 최종
실패로 판단하는 데는 확인된 치명적 비가역 결과가 필요하다.

## 선택한 구조

기존 공급자 보류·프로브, attempt 재개, queue의 원자적 갱신, 저장소 실행 잠금,
repo-operation 원장과 일반 workflow 인계를 연결한다. 별도 재시도 서비스나
특수 AI 수리 레인을 만들지 않는다.

화면만 바꾸는 방식은 작업이 멈추는 원인을 해결하지 못한다. 모든 종료를 새 작업으로
재실행하는 방식은 중복 writer·배포·외부 잡과 예산 초기화를 만든다.
기존 경로와 영속 필드를 연결하는 방식을 채택한다. 사용량 matcher·종료 판정·
preamble의 직접 원인을 먼저 수정하고 아래 회귀 검증을 실행한다. 그 뒤 남은
불변식 위반이 확인될 때만 소유 레코드의 최소 필드를 보강한다.

## 계약과 분류

dotfiles가 생성하는 `work-recovery-policy.json` schema 1과
`repo-operation-policy.json` schema 4를 핀된 원본 바이트·provenance로 갱신한다.
정본이 정의하는 disposition과 wait reason을 소비하고 다른 뜻으로 재정의하지 않는다.
모르는 버전은 원시 실패를 보존하고 자동 실행을 보류하며 실제 이유를 표시한다.

새 소비자는 기존 결과 문구와 `대기 · recovery:<reason>`을 함께 읽는다. parser와
두 계약의 검증이 통과한 뒤 시작하는 세션에만 `BDUI_WORK_RECOVERY_SCHEMA=1`을
전달한다. 지침은 이 값이 없는 Worker 세션에 새 문구를 요구하지 않는다. 이 값은
문구 지원 표시이며 승인·리뷰·재개 자격이 아니다. 기존 세션 환경은 변경하지 않는다.

분류 순서는 다음과 같다.

1. 실행·작업 identity와 기존 제어 상태를 읽는다. 사용자 중단, 사람 전용 설계·영수증
   대기, 폐기 절차는 자동 복구 대상으로 덮어쓰지 않는다.
2. 살아 있는 원래 writer, 결과 불명, 부분 효과·소유권 불명은 재조정 대상으로
   남기고 새 writer를 시작하지 않는다.
3. adapter가 증명한 공급자·사용량 조건, native 선행 관계·외부 잡 관측을 적용한다.
4. 승인 범위의 자체 결함과 정상 종료 줄의 복구 대기 의도를 적용한다.
5. 나머지는 `unclassified` 확인 대기로 보존한다. PR 부재·summary 부재·오류
   문자열·retry 소진만으로 최종 실패를 만들지 않는다.

초기 자동 fatal 목록은 비어 있다. 모델의 실패 주장만으로 fatal을 생성하지 않는다.
사람이 명시적으로 최종 실패로 판정한 원래 작업은 그 요청·증거와 기존 기록을
보존하고 자동 재개하지 않는다. 기존 실패 기록에는 이런 판정을 역으로 추정하지 않는다.

위험한 merge·hook 우회 명령의 기존 차단과 프로세스 종료는 유지한다. 해당 차단
이후 작업은 안전 판단 대기로 남고 자동 재발화하지 않는다. 승인 위조를 자동으로
다시 쓰거나 수리 Bead 생성으로 우회하지 않는다.

## 실제 사용량 제한 결함 수정

`server/worker/runner/codex-outage.js`의 구조화 오류 수집 경로에서
“You've hit your usage limit.”으로 시작하는 알려진 안내를 usage-limit로 인식한다.
기존 workspace-credit 문구와 JSON status envelope도 유지한다.

- 입력은 top-level `error`와 `turn.failed.error.message` 등 adapter가 이미
  오류로 수집한 레코드만이다.
- 일반 agent_message의 인용, 임의 stderr, “Failed to fetch workspace credits.”는
  usage-limit 증거가 아니다.
- “10:33 AM”처럼 날짜·시간대 없는 시각은 reset timestamp로 추정하지 않는다.
  `resets_at=null`로 기존 프로브가 해제를 판정하게 한다.
- live 종료와 persisted log 재조정 모두 같은 adapter 결과를 사용한다.
  최종 summary가 null이어도 raw 오류가 보류 근거다.
- 오류 안내·원래 종료 원인·기존 유효 summary를 보존한다. 이미 완료된 UI-lmqu의
  summary 보존과 업무 종료 판정을 되돌리거나 중복 구현하지 않는다.

계정 선택은 기존 사용자 허용 목록·attempt-local 정책만 따른다. 새 기본값이나
자동 provider/model 전환을 도입하지 않는다. 적용 가능한 계정이 없으면 대기한다.

## 기존 상태의 재사용과 재시작

원시 verdict·cause·로그·repo-operation 실패를 보존한다. 재개 계보는 기존
`resumed_from`, 다음 재개 예약은 `auto_resume_pending`, 반복 제한은 기존
`retry`와 공급자 hold, 원인 증거는 `cause_detail`을 사용한다. 별도 `recovery`
상태 기계·새 Beads status·승인 metadata를 도입하지 않는다.

재개 stage는 admission·publication·implementation·review·delivery·verify·
deploy·post_merge_job·cleanup 중 마지막으로 입증된 완료 단계의 다음 단계다.
세션·현재 SHA·유효 receipt·operation/cleanup cursor에서 재개할 때 계산한다.
자기 보고만으로 완료 단계를 넘기지 않는다. 근거가 충돌하면 읽기 관측만 허용하고
구현 재개를 예약하지 않는다. 계산한 stage의 영속 사본을 별도로 두지 않는다.

새 대기는 기존 paused/waiting/retry_wait 경로로 표현한다. 과거 failed attempt는
불변 이력으로 두고 현재 활성 계보의 원인 분류로 표시·입장 판단을 보완한다.
이력에서 failed였다는 사실 자체를 성공이나 미실패로 고치지 않는다.

같은 종료의 live callback·재시작 스캔이 겹쳐도 기존 queue revision 비교와
claim/잠금에서 재개 예약을 한 번만 소비한다. 응답을 잃으면 기존 재개 참조를
조회한다. 손상된 참조·누락된 로그·알 수 없는 실행은 보존 대기다.

직접 수정 뒤 무진전·중복 인계 회귀가 기존 필드의 공백을 입증하면
`cause_detail`에 입력/진전 비교값·무진전 횟수, 원래 operation의 인계 기록에
수정 Bead 참조만 추가할 수 있다. 비교 입력은 원래 계보·종료 attempt·stage·
승인 입력·현재 SHA·관련 operation identity로 한정한다. 기존 참조로 증명되는
항목은 중복 저장하지 않고, 실제 깨진 불변식과 보강 필드를 검증 결과에 남긴다.

## 자동 재개와 무진전 처리

재개는 기존 resume 경로를 사용한다. 다음 전제가 모두 충족돼야 한다.

- 원래 writer의 종료가 확인되고 다른 현재 writer가 없다.
- 기존 worktree, branch/HEAD, 작업 소유권과 부분 실행 효과가 확인됐다.
- 유효한 원래 승인·리뷰와 실행 선택이 남아 있다. 승인 공백을 채우지 않는다.
- 외부 조건이 해당 관측자로 해제됐으며 원래 레그의 재시도 정책도 재개를 허용한다.
- 같은 예약이 이미 소비되지 않았으며 원래 작업이 사용자 중단·폐기·완료되지 않았다.

자동 재개는 원래 provider/model/effort/speed와 허용된 계정 정책을 고정해 넘긴다.
새로운 workspace preset으로 바꾸는 기존 수동 선택은 자동 복구에 적용하지 않는다.
원래 session을 재개하고, 지원되지 않는 문맥을 새로 만들 때는 기존 fresh-session
허용 증거가 필요하다. 단지 실패·세션 ID 누락이라는 이유로 fresh를 시작하지 않는다.

재개 packet은 원래 목적·승인 artifact, 현재 상태와 변경, 완료된 검증·작업,
미완료 stage, 오류와 원래 효과, 남은 재시도 예산을 담는다. dotfiles-oeo1 사례는
검증된 구현 후보를 보존하고 중단된 리뷰를 처리한다. 유효한 리뷰 verdict가 없으므로
리뷰 완료로 간주하지 않으며, 리뷰 재발화·상한의 기존 규칙도 지킨다.
이미 생성된 외부 잡·PR·원장 intent는 먼저 조회하고 중복 생성하지 않는다.

같은 입력·같은 오류에 실제 진전이 두 번 없으면 자동 반복을 정지한다.
다음 시작에는 원인 정정, 관련 환경 회복의 관측, 또는 필요한 사람의 결정이 있어야
한다. 새 로그·시간·attempt 번호만으로 진전 판정이나 예산을 초기화하지 않는다.
레그 예산이 소진됐다면 프로브 성공만으로 그 상한을 우회하지 않고 해당 정책이
허용하는 재진입 또는 명시 결정까지 대기한다. 대기 시간이 길어져도 최종 실패가 아니다.

결과 불명은 원래 실행·효과를 기존 주기로 조회한다. 조회 예산이 끝나면 근거와
다음 조건을 남긴 확인 대기로 전환한다. 오래 기다렸다는 이유로 다른 writer를
시작하지 않으며 살아 있는 원래 실행의 claim을 경쟁 실행에 넘기지 않는다.

## 배포 실패와 수정 작업 인계

script_retry 1회를 소진한 종료 operation은 failed 그대로 남긴다.
결함이 소유 저장소의 수정 가능한 코드로 확인되면 일반 workflow 수정 Bead를
조회·재사용하거나 생성해 기존 Worker 대기열에 인계한다. 자동화 정책이 승인하는
경로이며 원본 이슈를 완료 처리하는 행위가 아니다.

인계 예약 키는 원래 operation id, target SHA, script/job identity와 원인이다.
원인 미확정이면 원래 실행 종료와 효과가 확인된 경우에만 기존 문의 경로에서
읽기 전용 진단을 한 번 예약한다. 소유 코드 결함이 입증되면 일반 workflow의
재사용·생성·검토·배치로 이어가고, 입증하지 못하면 확인 대기로 남긴다.
새 전용 실행 레인이나 가드 우회용 runner는 만들지 않는다.
원래 오류 로그, 승인 artifact, 실행 효과와 남은 완료 조건을 handoff에 포함한다.
중간 종료 후에는 기록된 수정 Bead와 실제 배치를 재조회해 이어간다.

인증·소유권·결과 불명, 사용자 결정 대기, 영수증 위조, 폐기 실패는 이 자동 수정
인계를 시작하지 않는다. 새 수정 이슈도 그 이슈의 승인·리뷰·배포 규칙을 따라야 한다.
같은 원인의 진행 중 수정 이슈가 있으면 재사용하며 반복 생성하지 않는다.

일회성 잡은 UI-j9j5의 explicit replaces·양방향 원자적 예약·원래 실패 기록·
정확한 실행 성공과 산출/clean 검증을 유지한다. 원래 실행이 live/unknown이면 수정
잡도 실행하지 않는다. 수정 성공 뒤 기존 cleanup-retry를 이어가고 원래 이슈의
닫힘까지 확인한다. 일반 배포는 검증된 대상과 descendant coverage의 기존
완료 규칙을 쓴다. 수정 PR 생성만으로 원래 작업을 완료시키지 않는다.

일반 코드 결함의 승인된 자동 인계만 ADR 0024가 승계한 사람 클릭 전용 규칙에서
제외한다. 원시 terminal 기록 시 기존 소유자가 알림을 한 번 남기는 규칙과
클래스·원인·다음 행동·링크, 재관측 시 알림 재생 금지, 기존 수동 재진입과 기록
세션·fork/fresh 사유, 살아 있는 해결 세션의 단일 소유, 설정 토글 없음은 유지한다.
폐기 실패의 세 출구, requested 아카이브 단계에서만 가능한 abandoned, 소유권
unknown 거부, owned runner의 SIGCONT 선행, 사용자 pause/stop 보호, 포기 기록·
이력 보존과 포기 알림 없음도 그대로 유지한다. 자동 인계가 폐기나 사람의 결정을
대신 실행할 권한을 주지 않는다.

## 표시와 기존 작업 적용

현재 상태는 기존 원인·상태 슬롯에 다음처럼 표시한다. 카드의 줄 순서·슬롯·조작
문법을 유지하고 새 배지·버튼·새 줄을 추가하지 않는다.

| 현재 상황 | 표시 | 동작 |
| --- | --- | --- |
| 보정 세션이 실행 중 | 복구 중 | 기존 실행 보기 |
| 조건·시간 관측 중 | 조건 대기와 구체 이유 | 기존 프로브/이어하기 |
| 원래 실행·효과 불명 | 확인 대기와 확인할 대상 | 기존 문의·로그 |
| 수정 이슈가 진행 중 | 수정 작업 대기와 이슈 참조 | 기존 이슈 이동 |
| 치명적 비가역 결과의 명시 확정 | 실패와 근거 | 자동 재개 없음 |

실패 필터·개수·행 조작도 현재 복구 상태와 일치해야 한다. 조건 대기를 실패로
집계하거나, 화면만 대기인데 scheduler가 영구 종단하는 상태를 허용하지 않는다.
재개가 불가능한 이유는 숨기지 않는다. 실패 이력과 로그는 계속 볼 수 있다.

배포 후 모든 등록 저장소의 미정리·미완료 실행에 기존 재조정 루프를 적용한다.
실제 오류 근거가 있는 건은 조건 대기로 분류하고, 원문이 없는 과거 실패는 확인
대기로 남긴다. 완료·폐기·숨김된 이력을 복원하거나 자동 재실행하지 않는다.
현재 돌고 있는 작업과 다른 세션의 변경을 건드리지 않는다.
Analysis-hkit·dotfiles-oeo1도 동일 규칙으로 처리하며 ID 특례를 만들지 않는다.

## 테스트 범위와 완료 기준

1. 실제 oeo1의 두 error 레코드를 비식별 fixture로 사용해 usage-limit 분류·보류를
   검증한다. summary=null, persisted raw 재조정, 모호한 시각도 포함한다.
   agent_message 인용·stderr·credit 조회 자체의 실패는 오탐하지 않는다.
2. 자체 형식 오류는 같은 세션 정정 지시를 받고, 중단됐으면 작업·변경을 보존한다.
   결과 줄 없는 종료, 일반 검증 red, 재시도 소진은 최종 실패가 아니다.
3. 같은 종료를 중복 전달하거나 예약 직후 재시작해도 재개가 하나다.
   live writer·결과 불명·소유권 충돌에서는 새 실행이 0개다.
4. 구현 완료/리뷰 중단 fixture가 리뷰 stage로 재개되고 원래 모델·승인·SHA·예산을
   유지한다. 이미 실행된 잡과 완료된 단계는 반복하지 않는다.
5. 두 번 무진전이면 자동 반복을 멈추고 대기한다. 입력 정정과 유효한 관측 후에만
   허용 범위에서 재개하며 guard kill·receipt forgery·parked를 우회하지 않는다.
6. 배포 실패는 raw failed 유지, 수정 인계 한 번, 중간 응답 손실 후 재채택,
   explicit replaces의 실제 성공 후 원래 cleanup 완료를 검증한다.
   원장 손상·live/unknown predecessor에는 수정 실행과 close가 없어야 한다.
7. 현재 대기/복구 표시·필터·개수가 실행 상태와 같고 실패 이력은 보존됨을 검증한다.
   기존 카드 문법과 UI-lmqu/UI-b1ry 회귀 테스트를 유지한다.

구현 worktree의 Node 버전·의존성 확인 뒤 관련 Vitest fixture/통합 검증,
`npm run tsc`, `npm run lint`, 변경 파일 Prettier, 전체 Vitest를 수행한다.
실제 공급자 호출이나 배포 부작용을 테스트의 오류 주입으로 발생시키지 않는다.

## 적용 순서와 중단 뒤 재개

1. dotfiles-9z2u의 계약·조건부 지침 배포와 원격/런타임 확인이 끝난 뒤, 해당 SHA의
   두 계약을 provenance와 함께 이 PR에 핀한다. schema와 구·신 종료 문구 네 조합을
   검증한다. 선행의 지침은 구 Worker에 새 문구를 출력하지 않아 혼재가 허용된다.
2. 기존 배포 operation과 `.worktrees/.repo-ops-deploy.lock`의 잠금 아래
   `repo-ops/script/deploy`를 실행한다. 시작 HEAD 확인 → npm ci/build → 재시작
   marker 시작 기록 → bdui-shared restart → health readback 순서는 기존 handler를 따른다.
3. health의 정확한 target SHA·worktree 경로·동일 instance와 서비스/bd 상태,
   최종 HEAD·tracked-clean을 확인한 뒤 종료 코드와 성공 marker를 재조회한다.
   단순 HTTP 200이나 프로세스 존재만으로 배포 성공을 주장하지 않는다.
4. 새 runtime이 두 계약과 parser를 실제 로드한 이후에만 새 세션에 준비 값을
   전달하고 새 자동 인계를 허용한다. 기존 세션의 종료도 읽을 수 있도록 구 문구
   해석을 유지하며, 진행 중인 세션을 새 환경 주입을 위해 재시작하지 않는다.
5. 기존 재조정 루프로 모든 등록 저장소의 미완료 실행을 관측한다. 원래 오류·
   계보·원장과 대기 이유/재개 조건을 읽고, 실행 전제가 충족된 작업만 기존 예약으로
   재개한다. 완료·폐기·사용자 중단을 되살리지 않는다.

중간 종료 시 원래 operation·재시작 marker·현재 runtime identity·재개 예약을 먼저
조회한다. 정확한 성공은 재채택하고 남은 단계만 진행한다. 결과 불명에서 배포나
작업을 중복 실행하지 않는다. 구 Worker에는 준비 값이 없고 새 runtime은 구 문구도
수용하므로 어느 경계에서 중단돼도 미지원 문구를 먼저 켜지 않는다. 새 영구 토글이나
별도 실행 장치는 필요하지 않다.

  - `summary`: "Worker는 원시 실패를 보존하면서 정본 복구 분류와 동일 계보의 단일 예약으로 미완료 단계만 수정·대기·재개한다"
  → ADR
