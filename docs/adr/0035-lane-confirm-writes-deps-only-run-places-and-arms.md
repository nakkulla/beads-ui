# 연결 레인 확정은 blocks 의존만 만들고 큐 적재와 arm은 ▶ 진행이 한다

## Context

모니터 연결 레인의 `확정`(`planLaneConfirm`, UI-j92s)은 인접 `dep-add`와 함께 어느
큐에도 없는 멤버를 각 레포 **병렬 큐**에 적재했다. UI-jaua가 더한 `▶ 진행`의 arm 축은
`auto_advance`가 OFF일 때만 후보를 좁히므로, 자동 진행이 켜진 레포에서는 병렬 큐 진입이
곧 발차다. 즉 확정 = 적재 = 발차가 되어 사용자가 `확정`을 "순서 저장"으로, `▶ 진행`을
"출발"로 읽는 구별을 화면이 지키지 않았다. 2026-09-03 `dotfiles-12su → UI-n28d`에서
확정만 눌렀는데 실행이 시작되는 것이 관측됐다.

같은 경로의 다른 구멍이 UI-ajkz다: 직렬 레인(`s1..s5`)에 앉은 멤버는 `unplaced`가
아니라 `▶ 진행`이 place하지 않고, `worker-queue-arm`은 병렬 행에만 쓰이므로 arm도
무시된다. 직렬 레인 멤버는 진행을 눌러도 발차되지 않았다.

## Decision

**확정은 durable 의존을, 진행은 실행 상태를 쓴다. 두 조작이 같은 것을 쓰지 않는다.**

- `확정`과 `재적용`은 인접 `blocks` 의존만 만들고 큐 적재를 하지 않는다. `queue_ops`는
  빈 배열이다. `재적용`의 의미는 "빠진 인접 의존 복구"만 남고, 그 버튼 조건
  `has_mismatch`는 `unplaced`를 세지 않는다 — 확정 뒤 큐 밖 멤버는 정상 상태이며 위치
  칩은 `미적재`가 아니라 `진행 대기`다.
- `▶ 진행`이 적재와 arm을 맡는다. 적재 대상은 "병렬 큐에 없는 행"이며, 직렬 레인에 있는
  멤버에게도 같은 `worker-queue-place { lane: 'parallel', index }`를 보내 서버가 원
  레인에서 빼고 병렬에 넣게 한다(현행 op 의미). 고정 행(실행중·PR 대기·완료)은 대상이
  아니다. 순서는 레포마다 place(들) → arm이고 revision 체이닝·부분 실패 토스트는 현행이다.
- 되돌리는 것은 만든 것뿐이다(UI-jaua §4). 진행이 옮긴 직렬 레인 멤버는 레인의 정지·삭제가
  되돌리지 않는다 — 되돌릴 durable 상태는 arm뿐이고 현행 `disarm`이 그것을 한다. 큐 위치는
  사용자가 다시 끌면 된다.
- 레포별 크로스레포 직렬 영역은 만들지 않는다. 순서 정본이 셋이 되고 arm 전파 경로를 다시
  깔아야 한다.

## Consequences

확정 뒤 멤버가 큐 순번을 미리 차지하지 못한다. 그 대가로 스케줄러에 새 후보 필터를 두지
않고 `arm`의 현행 의미(후보 확대)를 그대로 쓴다.

실재한 대안은 "큐에 넣되 보류 플래그로 후보에서 빼는 방식"이었다. 순번은 지키지만
`auto_advance` ON에서도 후보를 빼는 두 번째 축을 만들어 UI-jaua §5.2의 `armed_only`
규칙과 겹친다. 그래서 기각했다.

되돌리기 어려운 이유는 확정 레인의 큐 밖 멤버가 정상 상태가 되어 위치 칩(`진행 대기`)·
`재적용` 조건·`▶ 진행`의 적재 대상이 모두 그 전제 위에 서기 때문이다. `auto_advance` ON
레포에서 확정이 발차였던 과거를 모르면 분리 이유가 보이지 않는다.

UI-ajkz가 묻던 설계 선택(후보 1: 진행 시 병렬로 이동)은 이 결정이 닫는다. UI-jaua의 발차
축·위치 칩 결정은 유지되며, 큐 종류·순번은 그대로 툴팁에 남는다.
