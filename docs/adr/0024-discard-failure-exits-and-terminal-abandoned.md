# 폐기 실패의 출구는 셋이고 [폐기 포기]는 아카이브 단계 전용 terminal abandoned다

## Context

ADR 0022는 사용자 개시 작업의 terminal 실패를 자동 알림으로 관측하게 만들고,
재진입을 `[정리 재시도]`와 `[세션에서 해결]` **두 클릭**으로 닫았다. 그 결정의
전제는 "다시 누르면 언젠가는 통과한다"였다.

2026-08-31 `PROSTATE-0yz`가 그 전제를 반증했다. 폐기의 아카이브 단계가
`submodule_observation_failed`로 실패했고, 원인은 세션이 아니라 **저장소
상태**(`.gitmodules` 매핑 없는 고아 gitlink)였다. 사용자가 [재시도]를 두 번
눌렀고 두 번 다 같은 실패였다. 재시도가 원인에 닿지 않는 실패였기 때문이다.

그 상태에서 bead는 모든 조작이 막혔다. 활성 판정이 서버 여러 곳에서 각자
`phase !== 'done'`으로 구현되어 있어, 영구 실패한 작업이 계속 "진행 중"으로
읽혔다 — 재디스패치·직렬 레인 점유·대기 행 드래그·resume·pause·stop·merge·
cleanup·PR 관측 위임이 전부 차단됐다. `recover()`는 `!record.last_error`
조건으로 실패한 작업을 명시적으로 건너뛰므로 재시작으로도 풀리지 않았다.
`archiveDiscardSource()`가 owned runner에 보낸 SIGSTOP은 재시도를 위해
의도적으로 해제되지 않으므로, 그 runner는 얼어 있었다.

실제 출구는 서버를 세우고 `queue.json`을 손으로 고치는 것뿐이었다. 0022가 닫은
두 클릭 어느 쪽도 이 교착에 닿지 않는다.

## Decision

0022의 나머지 전부를 승계한다 — 알림은 durable terminal 기록을 쓰는 순간에 1건
자동 발송이고, `[정리 재시도]`와 기록 세션 resume 기반 `[세션에서 해결]`은 그대로
이며, 자동 수리 세션 dispatch 금지와 "설정 토글 없음"도 그대로다. 바뀌는 것은
**폐기 실패의 출구 개수 하나**다.

1. **폐기 실패의 출구는 셋이다.** 재클릭(=재시도), `[폐기 포기]`,
   `[세션에서 해결]`. 실패 알림의 `다음:` 줄이 이 셋을 말하고, 실패 행의 액션
   foot이 `[재시도] → [폐기 포기] → [세션에서 해결]` 순으로 같은 셋을 그린다.
   되돌리는 정도가 약한 것부터 읽히는 순서다.

2. **`[폐기 포기]`는 terminal phase `abandoned`다.** `done`과 똑같이 비활성이며,
   활성 판정은 `discardOperationActive()` 헬퍼 한 곳이 소유한다. 포기 뒤 그
   bead는 폐기 이전 자리로 돌아가고, 이어지는 `[폐기]`는 새 `operation_id`의 새
   작업을 만든다. `last_error`·`abandoned_at`·`abandon_resume`는 보존되어 무엇
   때문에 포기했는지가 재시작 뒤에도 남는다.

3. **포기는 `requested`(아카이브 단계) 실패에서만 진입한다.** 그 뒤 phase
   (runner 종료·PR 정리·revert·rollback)의 실패는 부분 수행 상태의 되돌리기
   계약이 따로 필요하므로 이 출구를 주지 않는다. 아카이브 단계는 아직 아무것도
   삭제하지 않은 유일한 지점이라, 포기가 "잃는 것 없음"을 뜻하는 구간도 여기뿐이다.

4. **소유권 판정 불능에서는 포기도 거부한다.** 포기는 SIGSTOP된 owned runner에
   SIGCONT를 먼저 보내고 그 다음에 상태를 쓴다. probe가 `unknown`(소유권 판정
   불능)이면 얼어 있는 runner가 남아 있을 수 있으므로 아무것도 쓰지 않고
   거부한다. `gone`·`recycled`는 되살릴 대상이 없다는 뜻이므로 그 상태를 기록한
   채 진행한다.

5. **포기가 남의 fence를 지우지 않는다.** 폐기가 자기 손으로 넣은 attempt만
   해제 대상이고, 사용자의 ⏸/■가 세운 정지는 그대로 남는다.

포기는 알림을 보내지 않는다. 0022의 알림은 "기계가 terminal 기록을 쓰는 순간"이
대상이고, 포기는 사람이 방금 누른 클릭의 결과다.

## Considered Options

- **재시도 한도 자동 종단.** N회 연속 같은 원인이면 기계가 terminal 처리한다.
  사용자 조작이 필요 없지만, ADR 0016의 "자동 종단 권한은 systemic 실패 계층만"과
  정면으로 어긋나고, 디스크 가득 같은 일시적 원인에서 성급히 포기한다. 기각.
- **백업 없는 폐기.** 잃을 고유 내용이 없음을 증명하면 아카이브를 건너뛴다.
  근본적이지만 "무엇을 잃지 않는가"의 판정 계약이 별도 설계이고, 되돌릴 수 없는
  작업의 안전장치를 판정 하나에 거는 셈이다. 기각.
- **모든 phase에서 포기를 허용한다.** 출구가 균일해 설명은 쉽지만, 이미 runner를
  죽이고 ref를 지운 뒤의 포기는 "아무것도 수행되지 않았다"가 거짓이 된다. 그
  상태의 정직한 종료는 되돌리기 계약을 먼저 정한 뒤의 일이다. 기각.
- **`phase: 'done'`으로 보낸다.** 활성 판정을 한 곳도 고치지 않아도 되지만,
  수행되지 않은 폐기가 완료로 기록된다. 상태가 거짓말하는 대가가 코드 변경보다
  크다. 기각.

## Consequences

- 쉬워지는 것: 아카이브가 성공할 수 없는 원인(저장소 상태·디스크·권한)이 있어도
  bead가 UI 조작만으로 다시 움직인다. 실패 원인 안내가 [재시도] 툴팁과 영수증
  줄에 붙어, 사용자가 무엇을 고쳐야 재시도가 통하는지 알고 누른다.
- 어려워지는 것: `abandoned`가 durable phase 어휘에 들어왔으므로, 활성 판정을
  새로 쓰는 코드는 `phase !== 'done'`이 아니라 `discardOperationActive()`를
  써야 한다. 새 활성 판정 지점이 생기면 그 헬퍼를 쓰는지가 리뷰 대상이다.
- 배제되는 것: 재시도 한도 자동 종단, 백업 없는 폐기, `requested` 밖 phase의
  포기, 소유권 판정 불능 상태에서의 포기, 포기의 Discord 알림.
- 남는 것: 폐기가 실제로 수행되지 않았다는 사실은 성공한 포기에만 쓰이는 결과
  이벤트로 이슈 상세 "Worker 이력"에 영구히 남는다. 카드에 영구 배지는 두지
  않는다 — 폐기 이전 상태로의 복귀가 곧 정직한 표시다.
