# Worker 한도 자동 전환은 사용자가 러너별로 고른 허용 계정 집합 안에서만 attempt 단위로 일어나고 자동 재개 cap을 소비하지 않는다

## Context

2026-08-24 공급자 보류 스펙 §8.3은 `usage_limit` 보류에서 "카탈로그의 건강한
계정 아무 곳"으로 자동 전환하는 규칙을 정했다. 2026-09-09 dotfiles-60u8(claude
러너)이 한도에 걸린 뒤 그 규칙이 Pro 요금제 계정을 골랐고, 그 계정에는 fable
모델이 없어 전환된 attempt는 다시 실패할 수밖에 없었다. 카탈로그(cswap·codex-auth)는
요금제·모델 가용성을 주지 않으므로 "건강한 계정"만으로는 받을 수 있는 계정을 알 수
없다. 같은 관측에서 계정 전환으로 태어난 자식이 §8.1의 자동 재개 1회 cap을
소비해, 전환 뒤 리셋 회복이 수동 조치로 남는 불편도 확인했다. 전환 판정은 claude
러너에만 있었고 codex 러너는 한도에서 타이머만 탔다.

검토한 대안: (1) 요금제 추론으로 후보를 거른다 — 카탈로그가 요금제를 모르고,
실패 문구로 학습하는 방식은 한 번은 반드시 실패해야 배운다. (2) 정책을 `bd kv`에
둔다 — hold 진입 판정은 mutation 안 동기 읽기여야 하고 kv에는 CAS가 없다.
(3) 워크스페이스 기본 계정을 갱신하는 전역 전환 — 다른 이슈·세션에 번지고 되돌림
규칙이 필요하다. (4) 전환 자식도 cap을 소비(현행 유지) — 계정 전환은 리셋 대기의
대체이지 "자동 재개"의 소비가 아니다. (5) 선제 전환이 Bead pin도 덮는다 — pin은
이슈 단위 명시 선택이고 아직 한도에 걸리지 않았다.

## Decision

- 전환 후보는 카탈로그의 모든 계정이 아니라 **사용자가 러너별로 고른 허용 계정
  집합**(`provider_limit_policy.<runner>.accounts`, 카탈로그 `key`)만이다. 카탈로그가
  요금제를 모르므로 자동 추론이 아니라 명시 선택이 정본이다. 집합이 비면 모드가
  `자동 전환`이어도 전환하지 않고 `'unconfigured'`로 타이머 경로에 남는다.
- 한도 시 동작은 러너별 `wait | switch` 모드다. 기존 워크스페이스 boolean
  `provider_auto_switch`는 큐 durable `provider_limit_policy` 객체로 대체되고 load
  이관은 한 방향이다(`false` → 두 러너 `wait`).
- claude·codex 두 러너가 같은 정책으로 전환한다. 전환 범위는 attempt 단위
  launch-only `exec_override`이며 워크스페이스 기본 계정·Bead pin·세션 계정은
  건드리지 않는다.
- 계정 전환으로 태어난 자식은 `auto_resume_kind:'account_switch'`로 스탬프되고
  §8.1 자동 재개 cap을 **소비하지 않는다** — cap은 리셋 뒤 자동
  재개(`provider_outage`)만 센다. 저장 사유 `'cap'`은 더 쓰지 않는다.
- 선제 전환은 선택이고 임계 퍼센트(`preempt_pct`)는 사용자가 정한다. 디스패치
  해석 시점에 **상속된 계정**(소스 `null`·`workspace_default`)만 대상이며 Bead
  pin(`'bead'`)은 덮지 않는다. 후보 건강 임계(5h 80%·그 외 창 90%)는 설정 키로
  만들지 않는다 — `preempt_pct`는 "언제 떠나는가", 그 상수는 "받는 계정이
  건강한가"다.
- 후보는 mutation 밖 비동기 카탈로그 조회로 고르므로 저장 단계가 같은 mutation
  안에서 허용 집합을 다시 확인한다.

## Consequences

- 사용자가 계정을 고르기 전에는 한도에서 전환이 일어나지 않는다. 이것이 의도된
  동작 변화다.
- 실행 패널 `실행 계정` 섹션에 러너별 모드·허용 계정 체크·선제 전환 퍼센트가
  생긴다. 카드 요소는 늘지 않고 팝오버·알림 문장만 바뀐다(ADR 0049 전제).
- Worker가 한도에 걸리기 전에 과금 풀을 바꿀 수 있다 — 선제 전환의 창 소모 대
  리셋 대기의 트레이드오프를 사용자 임계로 넘긴다.
- 전환 자식이 cap을 세지 않으므로 A→B 뒤 A가 리셋으로 회복하면 B→A가 다시
  가능하다. 한 시점에 보류 중인 계정으로는 돌아가지 않고 왕복은 창 리셋 주기보다
  빠를 수 없다는 것이 이 설계가 보장하는 전부다.
- 2026-08-24 스펙 §8.3의 후보 규칙("건강한 계정 아무 곳")은 이 결정으로 대체된다.
