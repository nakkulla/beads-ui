# 자동 진행 꺼짐은 대기 카드·요약에 표시하지 않고 저장소 자동화 토글만 말한다

## Context

UI-8gem은 큐 단위 사유를 슬롯 4a 게이트 칩 한 층으로 모으면서 `auto_advance_off`를
그 층에 놓았고, UI-cmx3은 그 사유와 `[지금 시작]` 버튼의 대상을 병렬 항목과 직렬
선두로 좁혔으며, UI-cmx3-2는 큐 단위 사정의 표시가 막힌 행의 4a 게이트 칩이라고
적었다. 세 결정 모두 "자동 진행이 꺼졌다"를 대기 행 위에 그린다는 전제를 공유한다.

2026-09-16 모바일 스크린샷(Monitor 병렬 영역)에서 그 전제의 비용이 드러났다. 자동
진행이 꺼진 저장소의 대기 카드마다 `⏸ 수동 출발` 칩과 `[지금 시작]` 버튼이
반복됐다. 이 사실은 저장소 단위이고 레포 카드의 자동화 토글(`▷`)과 Worker 툴바의
`▶ 자동화`가 이미 말한다. 유예 칩 `⏳ N초`는 더 나빠서, 자동 진행이 꺼져 있으면
스케줄러가 자동 출발 자체를 하지 않는데도 "남은 시간 동안 자동 실행이 미뤄집니다"
라고 말했다. 사용자는 한 건만 출발시키는 UI 경로가 사라지는 비용을 감수하고 표시
전부를 걷기로 결정했다(선두 행에만 버튼을 남기는 안은 기각).

읽는 화면이 하나도 남지 않으면 서버가 사유를 계속 싣는 것은 죽은 데이터다. 이
저장소는 이미 전체 스냅샷 재푸시의 크기 문제를 관측한 적이 있고, 사유를 남기면
`start_now` 조작 필터를 따로 둬야 한다. 그래서 서버 발행부터 멈춘다.

되돌리기 어렵다: 서버 사유 종류·`WaitKind` 어휘 표·범례·막힘 집계·두 탭 렌더와
테스트가 함께 묶인다. 맥락 없이 의외다: 자동 진행이 꺼진 저장소에서 한 건만
출발시키는 UI 경로가 없고, 코드만 보면 왜 게이트 칩 목록에 자동 꺼짐이 없는지
드러나지 않는다. 실재 대안이 있었다: 선두 행에만 버튼 유지, 칩만 제거하고 서버
사유 유지, 클라이언트만 무시. 한 조항이라도 뒤집히면 그 ADR 전체가 대체되므로 이
ADR은 UI-8gem·UI-cmx3·UI-cmx3-2의 유지 조항을 승계해 함께 싣는다.

## Decision

### 바뀐 조항

- 자동 진행 꺼짐(`auto_advance === false`)은 대기 카드에도 요약에도 표시하지
  않는다. 그 사실을 말하는 것은 레포 카드·Worker 툴바의 자동화 토글뿐이다.
- 서버는 `auto_advance_off` 사유를 내지 않는다. 그 사유 종류를 `WaitKind`에서
  빼고, 그와 함께 서버가 내던 유일한 `start_now` 조작도 없어진다. 다른 사유의
  대상 판정·verdict·알림·중복 억제 키는 그대로다.
- 클라이언트는 그 사유를 만들던 게이트(`⏸ 수동 출발`)를 만들지 않는다. 대신 대기
  행은 `manual_only`를 진다 — 그 행 저장소의 워크스페이스 상태 `auto_advance`가
  정확히 `false`일 때만 `true`이고, 값이 없거나 읽지 못하면 `false`로 두어 전과
  같이 그린다(fail-quiet).
- `manual_only` 행에는 대기 진입 유예 칩(4a)을 그리지 않고, 유예 때문에 서던
  `[지금 시작]`도 세우지 않는다. 그 행의 1초 유예 타이머도 켜지 않는다.
- `[지금 시작]`의 게이트 조건은 그대로다. 공급자 보류·큐 정지 게이트가 선 행은
  자동 진행이 꺼진 저장소에서도 버튼을 유지한다. 자동 진행이 켜진 저장소의 유예
  칩과 유예 `[지금 시작]`도 전과 같다.
- 막힘 요약 팝오버의 `큐: … 수동 출발 N` 항목을 없앤다. `큐:` 줄은 `정지 a`만
  남고, 비면 줄 자체가 서지 않는다.
- `worker-queue-start-now` op와 스케줄러의 `start_now_requests`·실행 직전 우회
  판정·`serial_lane_not_head`는 바꾸지 않는다. 사라지는 것은 서버가 그 op를
  제안하던 경로뿐이다.

### UI-8gem에서 승계하는 조항

- 카드의 대기 상태는 슬롯 1 배지 하나다. 배지는 종류 라벨(선행 대기·외부 계산·
  반영 대기·세션 대기·재시도 대기·처분 대기·한도 대기·공급자 장애)에 판정
  글리프(`⚠`·`⛔`)와 `지연`/`조치 필요`를 붙인다. held 종류가 있으면 라벨은 held
  종류의 것이고 판정은 같은 종류의 서버 사유가 준다. 같은 종류의 사유가 없으면
  종류 라벨만 그리고 `normal`로 추정하지 않는다.
- 사유가 여럿이면 대표 하나를 고른다: verdict 심각도(`action_required` >
  `overdue` > `normal`) 다음 종류 순서(`awaiting_user` > `stale_work` > `recovery`
  > `provider_hold` > `prerequisite_foreign` > `prerequisite` > `base_moved` >
  `retry_wait`). 나머지 사유와 해제 조건·판정 근거는 배지 팝업이 싣고, 카드
  본문은 대표 사유의 headline 한 줄이다.
- 큐 단위 사유(`queue_hold`와 큐 행의 공급자 게이트)는 슬롯 4a 게이트 칩 하나로만
  선다. 배지·본문·시각을 만들지 않고 막힘 집계에 들지 않는다. 보류된 attempt의
  `provider_hold`는 그 이슈의 사정이므로 배지와 집계에 남는다.
- `막힘 N`은 이슈 단위 사유가 하나라도 있는 원래 이슈 수다. `external_job`은 원래
  이슈로 한 번 세고, 큐 단위 사유(`queue_hold`)는 팝오버의 `큐:` 줄로만 건수를
  남긴다.
- 새 대기 종류나 사유는 어휘 표에 행을 더하고 이 규칙(대표 사유·scope)에 따라
  배지 또는 게이트 칩 어느 한 층에만 놓는다. 두 층에 동시에 그리는 변경은 이
  결정의 supersede가 필요하다.

### UI-cmx3에서 승계하는 조항

- 직렬 레인은 순서대로 쌓는다. 후보 수집은 점유되지 않은 직렬 레인의 선두
  (`entries[0]`) 하나만 후보에 넣고, 선두가 어떤 이유로든 실행 불가면 레인은 그
  pass 를 기다린다. 확인된 선행 대기(`prerequisite_unmet`)를 건너뛰는 예외는 없다.
  선두가 `!ready || blocked`이면 선행 대기 진단(`recordNotReady`)은 선두에만
  기록한다.
- 실행 전과 실행 직전의 두 검사는 같은 동기 판정 `serialHeadOf`를 쓴다: 레인 밖이면
  통과, 레인이 있으면 선두일 때만 통과, 아니면 `serial_lane_not_head`다. 비동기 준비
  중 드래그로 선두가 바뀌면 직전 검사가 실행을 중단한다. `bypassed_before`·
  `verifySerialBypass`·`serialBypassLocallyBlocked`는 두지 않는다.
- `[지금 시작]`은 지정한 이슈 하나의 실행 권한이다. 선두가 아닌 직렬 항목을
  지정하면 후보 수집 시점에 `serial_lane_not_head`를 기록하고 요청을 소비하며,
  뒤 항목으로 권한을 넘기지 않는다. 자동 진행이 켜진 저장소에서 유예·게이트로
  서는 `[지금 시작]` 버튼도 직렬 선두가 아닌 행에는 서지 않는다.
- 레인 단위·항목 단위의 우회 옵트인 설정을 두지 않는다. 우회가 필요하면 사람이
  항목을 병렬로 옮기거나 재정렬한다. 선두 대기 중인 뒤 항목에 새 칩을 만들지
  않는다.
- (UI-wc67 승계) 연결 레인은 폐기한다. 의존 관계는 일반 `blocks` 간선, 실행
  위치는 저장소별 병렬·직렬 대기열만 사용한다. 전용 프로토콜·저장소·투영·진행
  권한과 조작을 제거하며 저장소별 크로스레포 대기 영역이나 새 영구 실행 권한을
  만들지 않는다.
- (UI-wc67 승계) 대기 중 이슈는 레인·상대 순서·진입 시각을 보존한다. 닫힌 이슈는
  기존 완료 정리로 제외한다.
- (UI-wc67 승계) 직렬 실행은 한 번에 하나다. 실행 예약과 실행 중·PR 대기·정리 중
  계보의 기존 점유를 보존한다. 후보 선택과 명시적 시작, 예약과 실행 직전 확인은
  같은 순서를 판정한다.
- (UI-wc67 승계) 자동 진행과 자동 머지는 ADR 0011처럼 별개이고 기본값도 유지한다.
- (UI-wc67 승계) ADR 0034의 외부 활동 이벤트·대기 재검사 경로를 계속 사용한다.
  요청 저장소의 `bd ready`가 확인한 이슈만 선행 대기를 지우고 원래 자리에서 보통
  실행 후보로 복귀한다. 이미 실행 중인 뒤 항목을 선점하지 않는다. 조회 실패나
  순환 의존은 해소됐다고 추측하지 않는다.
- (UI-wc67 승계) 기존 `blocks` 간선·대기열·실행 세션·완료 이력은 보존한다. 과거
  provenance를 근거로 의존을 지우지 않는다. `cross-lanes.json`은 읽기·쓰기·자동
  삭제·이관 없이 퇴역 자료로 남기며 그 파일의 멤버를 자동 적재하지 않는다.
- (UI-wc67 승계) 과거 큐와 attempt의 arm 필드는 실행·머지 권한으로 소비하지 않고
  새 정규화와 저장에서는 만들지 않는다. 과거 이력 파일은 다시 쓰지 않는다. 이미
  머지 대기열에 등록된 유효한 권한과 실행 중 세션은 취소하지 않는다.
- (UI-lmqu 승계) `waiting`은 종료된 attempt의 기계 사실 대기이며 실패나 사람의
  설계 결정 대기가 아니다. 기존 `TERMINAL_ATTEMPT_STATUSES`와 정산 경로를 사용하고
  실행 슬롯을 해제한다. 새 Beads 상태·metadata·가짜 의존성은 만들지 않는다.
- (UI-lmqu 승계) `prerequisite_unmet`은 기존 선행 증명을 사용한다. 이 사유의 유일한
  fence는 `bd ready` 부재이며 선행 해소 뒤 보통 후보로 새 attempt를 실행한다. 기존
  이벤트 구독과 준비 상태 재검사, 선행 링크를 유지한다. 관측 오류나 모호한 결과는
  대기로 추정하지 않는다.
- (UI-lmqu 승계) `base_moved`는 종료 표식의 후보와 기준 SHA를 검증한 경우만
  인정한다. 현재 attempt가 소유한 worktree·branch·head, 후보 부모와 기록 기준의
  일치, 후보에 결속된 검증·리뷰, 원격 이동과 미인도를 확인한다. 이미 인도한 후보는
  기존 실제 인도 증거로 정산한다. 코드 검증 실패나 소유권·원격 관측 불명은 대기로
  낮추지 않는다.
- (UI-lmqu 승계) 기준 이동 후보는 기존 `quickfix_landing`에 `cursor=null`,
  `head_sha=<candidate>`, `reason=base_moved`로 보존한다. 기준 SHA는 검증된 종료
  표식에서 복구한다. `target_base`는 브랜치 이름으로 유지하며 후보 SHA 자체를 인도
  증거로 삼지 않는다.
- (UI-lmqu 승계) 기준 이동 대기는 자동 새 구현을 막는다. `↻ 이어하기`만 기록된
  세션·provider와 같은 worktree·branch·후보를 검증해 최신 기준 반영부터 재개한다.
  참조나 후보가 없으면 그 사유로 거부하며 새 세션·worktree 생성이나 잔여물 회수로
  대체하지 않는다. 관계없는 Beads 이벤트로 fence를 지우지 않는다.
- (UI-lmqu 승계) 기준 이동 카드는 기존 슬롯 1 상태에 `반영 대기`, 같은 조작 슬롯에
  공통 `.op-btn`인 `↻ 이어하기`를 표시한다. 기계 정리 재시도는 별도 기존 출구를
  유지한다.

### UI-cmx3-2에서 승계하는 조항

- 화면 대표는 "무엇을 기다리나"가 정한다. 실행 중 그리드는 세션이 돌거나(running·
  paused) attempt 자체를 사람이 처리해야 하는 것(failed·parked·retry_wait·
  provider_hold, `base_moved`·recovery `waiting`)만 담는다. 선행을 기다리는 bead는
  대기 행이다.
- 강등 판정의 재료는 attempt의 `cause` 하나다: `run_state === 'waiting'`이고
  `attempt.cause === 'prerequisite_unmet'`이면 `activeByBead`는 타일을 만들지 않고
  `claimed`에도 넣지 않아 그 bead의 기존 대기 행(병렬 큐·직렬 레인 entry)이 자기
  레인·순번·진입 시각을 지킨 채 대표한다. `cause`가 `base_moved`·recovery 계열이거나
  미상이면 현행대로 타일이다(fail-closed). Worker·Monitor는 같은 `buildLanes`를 쓰므로
  함께 바뀐다(ADR 0014).
- 기록은 바꾸지 않는다. `waiting` attempt·admission·`wait_notified`·타임라인은
  불변이고(ADR 0029·0027), 강등은 화면 대표만 바꾼다. 다음 attempt가 dispatch되면
  옛 레코드는 저절로 대표에서 물러나므로 대기 행에 폐기 출구를 두지 않는다.
- 새 어휘·새 칩·새 레인은 없다. `복귀 대기` 배지·어휘와 서버의 `return_overdue`
  지연 판정은 두지 않고, 막던 선행이 해제된 사실은 대기 행 4b의 기존 `🔓 <ID>` 칩이
  말한다 — 선행 대기 기록(`waiting/prerequisite_unmet` attempt 또는
  `prerequisite_unmet` admission)이 있는 대기 행은 동결 선행에서 지금 열린 선행을
  뺀 나머지를 그 칩의 재료로 얻는다(UI-d13v "후보 행만"의 예외). 열린 선행이 하나도
  없으면 서버는 `prerequisite` 사유 자체를 내지 않고, 행에는 `⛓` 칩도 배지도 흐림도
  서지 않는다.
- 선행 대기의 시각 정보는 판정 없이 이슈 상세 의존성 절의 참고 줄 하나로만 남긴다
  (선행 대기 시작 · 해제 · 해제 후 경과). 외부 작업·공급자 보류의 지연 판정과 알림은
  유지한다.

## Consequences

자동 진행이 꺼진 저장소의 대기 카드는 조용하다. 저장소 단위 사실이 행 수만큼
반복되지 않고, 사실과 다른 유예 안내도 사라진다. 대신 자동 진행이 꺼진 저장소에서
한 건만 출발시키는 화면 경로가 없다 — 출발시키려면 자동화 토글을 켜거나 툴바
`▶ 자동화`를 쓴다. 게이트에 막힌 행의 `[지금 시작]`은 남으므로 큐 정지·공급자 보류
아래에서 한 행을 지금 돌리는 권한은 그대로다.

서버 `wait_reasons`에서 `auto_advance_off` 종류가 사라지므로 이 사유를 읽던 소비자는
아무것도 받지 못한다. 저장소 밖 소비자는 없고(dotfiles 계약은 대기 사유 어휘를
정의하지 않는다), 저장소 안에서는 어휘 표·범례·집계·두 탭 렌더가 함께 지워졌다.
자동 진행 꺼짐을 다시 대기 행 위에 그리려면 이 결정의 supersede가 필요하다.

기각한 대안: 선두 행에만 `[지금 시작]` 유지(자동 꺼짐 표시가 카드에 그대로 남는다),
칩만 제거하고 서버 사유 유지(소비자 없는 사유가 스냅샷에 남고 `start_now` 조작
필터를 따로 둬야 한다), 서버는 그대로 두고 클라이언트만 무시(같은 문제에 더해 두
층의 규칙이 갈린다).
