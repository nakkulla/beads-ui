# 병렬성 분석 기능 전면 제거와 수동 배포 실행

## Context

체인: 2026-08-12 `worker-parallelism-analysis`가 병렬성 분석을 도입했고, 08-18
`parallel-analysis-codex-runner`, 08-19 `parallel-analysis-observability`, 08-20
`parallel-analysis-scope-signal`이 각각 실행 경로·관측·범위 신호를 얹었다. spec
4건의 투자였다. 2026-08-27 `worker-repo-ops-cleanup-deploy-button`이 그 기능을
통째로 제거했다.

기능이 산출한 것은 "이 항목들을 함께 돌려도 된다"는 추천이었는데, 그 추천을
받아들이는 판단은 결국 사람이 했고, 추천을 만들기 위한 분석 실행·관측 표면·
프로토콜 메시지는 계속 유지 비용을 냈다. 추천의 정확도를 높이는 방향으로 세 번
확장했지만 사람이 그 결과를 신뢰해서 자동으로 쓰는 단계에 도달하지 못했다.

## Decision

병렬성 분석 기능을 코드·테스트·프로토콜까지 제거한다. 남는 것은 수동
`[배포 실행]` 버튼 하나다 — 사람이 저장소 작업 화면에서 직접 누른다.

해소 사다리는 `script_retry` 한 단계로 축소하고, **토글 없이 상시**다. 분석
결과에 따라 자동화 수준을 바꾸는 스위치가 없어졌으므로 토글이 가리킬 대상도
없다. 2026-08-13의 lane-scheduling은 이 결정의 범위 밖으로 남긴다.

## Considered Options

- **기능을 그대로 유지한다.** 4건의 spec 투자를 보존하지만, 유지 비용이 실제
  사용으로 상환되지 않는 상태가 계속된다. 매몰비용을 근거로 삼지 않기로 했다.
- **축소해서 남긴다(분석만, 추천 없이).** 표면은 줄지만 프로토콜·관측 경로는
  그대로 남아 비용의 대부분이 유지된다. 절반만 남기면 "이건 뭘 위한 건가"라는
  질문만 영구화되므로 기각했다.

## Consequences

- 쉬워지는 것: 저장소 작업 화면이 "무엇을 실행할지"를 사람이 정하는 단순한
  모델이 된다. 분석 컨텍스트·프로토콜 메시지·관측 필드가 사라져 큐 상태가
  작아진다.
- 어려워지는 것: 함께 돌려도 되는 항목을 사람이 판단해야 한다. 그 판단을 돕는
  기계 신호는 없다.
- 배제되는 것: 분석 결과를 입력으로 삼는 자동 그룹화, 그리고 자동화 수준을
  조절하는 사용자 토글. 분석 인프라 중 재사용 가치가 있던 조각(target 스냅샷)은
  독립 모듈로만 남았다.
