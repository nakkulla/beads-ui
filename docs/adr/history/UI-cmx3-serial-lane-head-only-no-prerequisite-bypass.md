# 직렬 레인은 선두만 실행 후보이고 선행 대기 우회 예외는 없다

## Context

ADR UI-wc67은 연결 레인을 폐기하면서 직렬 레인에 한 가지 예외를 두었다: 비어 있는
직렬 레인을 저장 순서로 살피되 실제 미해결 선행을 확인한 `prerequisite_unmet` 항목만
건너뛰고, `[지금 시작]`도 같은 순서 예외를 따른다. ADR UI-lmqu는 `waiting`의 사유별
분기를 정하면서 "직렬 레인의 확인된 선행 대기만 추월하는 규칙을 유지한다"고 썼다.

2026-09-16 microbiome_bile 워크스페이스 관측에서 이 예외의 비용이 드러났다. 직렬
레인 s1의 세 항목이 차례로 선행 미충족 `waiting`으로 끝나 실행 중 그리드에 held
타일 세 개가 남았고, 우회 검사(`verifySerialBypass`)는 앞 항목 전부를 두 번 재조회해
"선행 대기만 건너뛰기"를 증명해야 했다. 사용자의 판단은 직렬 배치 자체가 순서
의도(산출물·문서 겹침, 착지 순서)라는 것이다. 우회는 착지 순서를 뒤집어 rebase
비용을 겹침이 큰 곳에서 발생시키고 시스템 전체 in-flight를 늘리며, 스케줄러가
사용자의 순서를 재해석하는 규칙을 하나 더 만든다.

되돌리기 어렵다: 스케줄러의 후보 수집·두 번의 실행 전 검사·`[지금 시작]` 경계·
`auto_advance_off` 대상·seam D 테스트가 "선두만"에 묶이고, 되돌리려면 두 번
재조회하는 우회 검사를 다시 지어야 한다. 맥락 없이 의외다: 이틀 전 같은 사용자가
반대 방향(UI-wc67)을 결정했고, 코드만 보면 "선두가 놀고 있는데 왜 뒤가 가지
않는가"가 설명되지 않는다. 실제 절충이 있다: 선두가 외부 선행에 오래 묶이면 레인이
놀고 사람이 옮겨야 한다. 한 조항이라도 뒤집히면 그 ADR 전체가 대체되므로 이 ADR은
UI-wc67·UI-lmqu의 유지 조항을 승계해 함께 싣는다.

## Decision

### 바뀐 조항

- 직렬 레인은 순서대로 쌓는다. 후보 수집은 점유되지 않은 직렬 레인의 선두
  (`entries[0]`) 하나만 후보에 넣고, 선두가 어떤 이유로든 실행 불가면 레인은 그
  pass 를 기다린다. 확인된 선행 대기(`prerequisite_unmet`)를 건너뛰는 예외는 없다.
  선두가 `!ready || blocked`이면 선행 대기 진단(`recordNotReady`)은 선두에만 기록한다.
- 실행 전과 실행 직전의 두 검사는 같은 동기 판정 `serialHeadOf`를 쓴다: 레인 밖이면
  통과, 레인이 있으면 선두일 때만 통과, 아니면 `serial_lane_not_head`다. 비동기 준비
  중 드래그로 선두가 바뀌면 직전 검사가 실행을 중단한다(UI-wc67의 "최신 상태로
  재판정" 경계 유지). `bypassed_before`·`verifySerialBypass`·
  `serialBypassLocallyBlocked`는 삭제한다.
- `[지금 시작]`은 지정한 이슈 하나의 실행 권한이다(UI-wc67 4항 앞부분 유지). 선두가
  아닌 직렬 항목을 지정하면 후보 수집 시점에 `serial_lane_not_head`를 기록하고 요청을
  소비하며, 뒤 항목으로 권한을 넘기지 않는다. 자동 진행이 꺼진 큐의 `auto_advance_off`
  사유와 `[지금 시작]` 버튼은 병렬 항목과 직렬 선두에만 선다.
- 레인 단위·항목 단위의 우회 옵트인 설정을 두지 않는다. 우회가 필요하면 사람이
  항목을 병렬로 옮기거나 재정렬한다. 선두 대기 중인 뒤 항목에 새 칩을 만들지 않는다.

### UI-wc67에서 승계하는 조항

- 연결 레인은 폐기한다. 의존 관계는 일반 `blocks` 간선, 실행 위치는 저장소별
  병렬·직렬 대기열만 사용한다. 전용 프로토콜·저장소·투영·진행 권한과 조작을
  제거하며 저장소별 크로스레포 대기 영역이나 새 영구 실행 권한을 만들지 않는다.
- 대기 중 이슈는 레인·상대 순서·진입 시각을 보존한다. 닫힌 이슈는 기존 완료 정리로
  제외한다.
- 직렬 실행은 한 번에 하나다. 실행 예약과 실행 중·PR 대기·정리 중 계보의 기존
  점유를 보존한다. 후보 선택과 명시적 시작, 예약과 실행 직전 확인은 같은 순서를
  판정한다.
- 자동 진행과 자동 머지는 ADR 0011처럼 별개이고 기본값도 유지한다.
- ADR 0034의 외부 활동 이벤트·대기 재검사 경로를 계속 사용한다. 요청 저장소의
  `bd ready`가 확인한 이슈만 선행 대기를 지우고 원래 자리에서 보통 실행 후보로
  복귀한다. 이미 실행 중인 뒤 항목을 선점하지 않는다. 조회 실패나 순환 의존은
  해소됐다고 추측하지 않는다.
- 기존 `blocks` 간선·대기열·실행 세션·완료 이력은 보존한다. 과거 provenance를
  근거로 의존을 지우지 않는다. `cross-lanes.json`은 읽기·쓰기·자동 삭제·이관 없이
  퇴역 자료로 남기며 그 파일의 멤버를 자동 적재하지 않는다.
- 과거 큐와 attempt의 arm 필드는 실행·머지 권한으로 소비하지 않고 새 정규화와
  저장에서는 만들지 않는다. 과거 이력 파일은 다시 쓰지 않는다. 이미 머지 대기열에
  등록된 유효한 권한과 실행 중 세션은 취소하지 않는다.

### UI-lmqu에서 승계하는 조항

- `waiting`은 종료된 attempt의 기계 사실 대기이며 실패나 사람의 설계 결정 대기가
  아니다. 기존 `TERMINAL_ATTEMPT_STATUSES`와 정산 경로를 사용하고 실행 슬롯을
  해제한다. 새 Beads 상태·metadata·가짜 의존성은 만들지 않는다.
- `prerequisite_unmet`은 기존 선행 증명을 사용한다. 이 사유의 유일한 fence는
  `bd ready` 부재이며 선행 해소 뒤 보통 후보로 새 attempt를 실행한다. 기존 이벤트
  구독과 준비 상태 재검사, 선행 링크를 유지한다. 관측 오류나 모호한 결과는 대기로
  추정하지 않는다.
- `base_moved`는 종료 표식의 후보와 기준 SHA를 검증한 경우만 인정한다. 현재
  attempt가 소유한 worktree·branch·head, 후보 부모와 기록 기준의 일치, 후보에
  결속된 검증·리뷰, 원격 이동과 미인도를 확인한다. 이미 인도한 후보는 기존 실제
  인도 증거로 정산한다. 코드 검증 실패나 소유권·원격 관측 불명은 대기로 낮추지
  않는다.
- 기준 이동 후보는 기존 `quickfix_landing`에 `cursor=null`, `head_sha=<candidate>`,
  `reason=base_moved`로 보존한다. 기준 SHA는 검증된 종료 표식에서 복구한다.
  `target_base`는 브랜치 이름으로 유지하며 후보 SHA 자체를 인도 증거로 삼지 않는다.
- 기준 이동 대기는 자동 새 구현을 막는다. `↻ 이어하기`만 기록된 세션·provider와
  같은 worktree·branch·후보를 검증해 최신 기준 반영부터 재개한다. 참조나 후보가
  없으면 그 사유로 거부하며 새 세션·worktree 생성이나 잔여물 회수로 대체하지 않는다.
  관계없는 Beads 이벤트로 fence를 지우지 않는다.
- 기준 이동 카드는 기존 슬롯 1 상태에 `반영 대기`, 같은 조작 슬롯에 공통 `.op-btn`인
  `↻ 이어하기`를 표시한다. 기계 정리 재시도는 별도 기존 출구를 유지한다. 선행 대기
  attempt의 화면 대표는 ADR UI-cmx3-2가 정한다.

## Consequences

`A → B → C`에서 A가 외부 선행을 기다리면 B·C는 그 선행이 닫힐 때까지 기다린다.
레인이 놀지 않게 하는 것은 사람이며, 대기 행의 `⛓ 선행 대기`(A)와 순번(B·C)이 그
판단의 근거다. 세션이 분리한 선행 quick_fix는 원 이슈 앞 index에 놓이고 레인 보정도
같은 결과를 내므로 순서대로 쌓아도 흐른다. 레인당 동시 실행 1은 전과 같고, 줄어드는
것은 착지 순서 뒤집힘과 시스템 전체 in-flight다. 직렬 순서 확인은 다시 단순한 맨 앞
비교가 된다.

기각한 대안: UI-wc67 유지(직렬 배치 의도를 스케줄러가 뒤집는 문제가 그대로), 기본
쌓기 + 레인 단위 우회 옵트인(설정 저장·UI가 늘고 규칙이 둘이 된다).
